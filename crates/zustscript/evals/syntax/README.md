# 文法の改善ループ (evals/syntax)

zustscript の文法の変更を、**提案 → 人が読む → subagent がルーブリックで評価 → 改訂** の繰り返しで詰めるための置き場所。
実装は、提案が「採用」になってから行う(実装したら、提案のサンプルを `examples/` と tests に移す)。

## ファイル

| パス | 中身 |
|---|---|
| `rubric.md` | 評価の観点(R1〜R8)と、1〜5 点の基準。どの評価でも同じものを使う |
| `personas.md` | 評価者の立場(TS 開発者、wasm_bindgen を使う Rust 開発者、言語の実装者)。立場ごとに重く見る観点が違う |
| `proposals/NNN-name.md` | 提案。動機、変更前後のコード、JS / `.d.ts` の出力、代替案、未決事項。決まった書式(下) |
| `corpus/*.zsc` | 評価に使う現実的なプログラム(今の文法)。提案は、これらを書き換えた版を「変更後」として載せる |
| `prompts/evaluate.md` | 評価役の subagent に渡す指示(読むもの、出力の形式) |
| `prompts/write.md` | 「書かせる評価」の指示: 提案だけを読んで課題のプログラムを書かせ、誤用や迷いを集める |
| `results/NNN-name/rK-persona.json` | 評価の結果(K は改訂の回)。形式は `prompts/evaluate.md` |
| `results/NNN-name/summary.md` | 回ごとの点の推移、出た指摘と、その扱い(採用 / 却下とその理由) |
| `tools/summarize.py` | `results/` の JSON を集計して点の表を出す |

## ループ

1. **提案を書く**: `proposals/NNN-name.md`。`corpus/` のどれかを書き換えた「変更後」を必ず含める。抽象的な説明だけでは評価できない
2. **人が読む**: 方向が違えば、ここで直す(subagent を回す前に)
3. **評価(rK)**: 3 つの persona それぞれの subagent に `prompts/evaluate.md` を渡す。互いの結果は見せない(引きずられないように)。結果は `results/NNN-name/rK-<persona>.json`
4. **集計**: `python3 tools/summarize.py results/NNN-name`。観点ごとの点と、指摘の一覧が出る
5. **改訂**: 指摘ごとに、採用 / 却下(理由つき)を `summary.md` に書き、提案を直す。採用した点は提案の「改訂履歴」に残す
6. **再評価(rK+1)**: 3〜5 を、点が頭打ちになるか、残った指摘が設計上のトレードオフだけになるまで
7. **書かせる評価**: `prompts/write.md` で、提案を読んだだけの subagent に課題を書かせる。読み違えた箇所は説明か文法の問題
8. **決定**: 人が採用 / 保留 / 却下を決める。採用なら実装し、提案のサンプルを `examples/` と tests に移す

## 提案の書式

```text
# NNN: 題名
状態: 草案 | 評価中 (rK) | 採用 | 保留 | 却下
## 動機            今の文法で困ること(corpus の具体例で)
## 提案            文法(書き方)と意味。曖昧さの解き方
## 変更前 / 変更後   corpus のプログラムの書き換え
## 出力            JS と .d.ts(と、関わるなら Rust / wasm)
## 代替案          検討した別の書き方と、選ばなかった理由
## 未決事項
## 改訂履歴         rK の指摘で何を変えたか
```

## 評価の前提(評価者にも渡す)

- 決まっている設計方針: TS 風の見た目、class なし、純粋関数型を基本にする(ローカル変数の可変性だけ許す)、数値の型を明示する(暗黙の変換なし)、クロージャは `(x) => e`、配列は `readonly T[]`、型で明示的に作る(typed array など)
- enum の JS での表現(`TAG` など)は保留中。`@tag(..)` のようなディレクティブで選べるようにする案がある。提案は、表現が変わっても成り立つように書く
