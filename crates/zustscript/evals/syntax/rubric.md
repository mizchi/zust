# ルーブリック

各観点を 1〜5 点で付ける。点には必ず根拠(提案や corpus の具体的な行)を付ける。迷ったら低い方を付け、何があれば上がるかを書く。

| ID | 観点 | 5 | 3 | 1 |
|---|---|---|---|---|
| R1 | **読みやすさ** (初見の TS / Rust 開発者が意味を取れるか) | 説明なしで正しく読める | 一度説明を読めば分かる | 読み違えやすい、記号が多い |
| R2 | **一貫性** (既存の文法・決定事項と揃っているか) | 既存の規則の自然な延長 | 例外が 1 つある | 似た機能に別の書き方が混在する |
| R3 | **曖昧さのなさ** (人にとっても構文解析にとっても、1 通りに読めるか) | 先読み 1 トークンで決まり、人も迷わない | 文脈(期待する型など)で決まるが、規則は明快 | 同じ字面が複数の意味を持ち、規則も込み入る |
| R4 | **簡潔さと表現力** (よくある処理が短く書けるか、書けないことが増えないか) | よくある処理が短くなり、失うものがない | 長さは同じ程度、または一部が長くなる | 冗長になる、または書けないものが出る |
| R5 | **誤りにくさ** (間違えたときに分かるか。静かに別の意味にならないか) | 誤りはコンパイル時に、位置と直し方つきで分かる | 分かるが、メッセージが分かりにくい | 誤りが別の正しいプログラムとして通ってしまう |
| R6 | **出力の予測しやすさと TS との相互運用** (JS / `.d.ts` の形が予想でき、TS から自然に使えるか) | 出力が見なくても予想でき、TS 側でそのまま使える | 予想できるが、TS 側で一手間要る | 出力が驚くような形、または TS から使いにくい |
| R7 | **移行と学習のしやすさ** (JS / TS / Rust の経験がそのまま使えるか) | 知っている書き方がそのまま通じる | 新しく覚えることが少しある | 独自の概念を多く覚える必要がある |
| R8 | **実装と道具** (構文解析・型検査・増分ビルド・LSP(補完、hover)に無理がないか) | 局所的に決まり、補完・エラー回復もしやすい | 型情報が要るが、無理はない | 大域的な解析が要る、補完やエラー回復が難しい |

## 点のほかに必ず出すもの

- **blocker**: 採用できない理由になる問題(なければ空)
- **issues**: 具体的な指摘。重さ(high / medium / low)、該当箇所、直し方の案
- **questions**: 提案が答えていない問い(未決事項に足すべきもの)
- **alternative**: 提案より良いと思う書き方があれば、その例
