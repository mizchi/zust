# zustscript の公開関数を初見で書けるか

言語 README とコンパイラを渡し、配送ラベルと波形の二乗和をそれぞれ別の subagent に実装してもらいました。**8 試行とも最初のコンパイルで目的のモジュールができました。** 公開関数を書いた全員が `export fn` を選び、Wasm を使った 4 人は `@wasm export fn` の順序も初回から正しく書けています。

| 課題 | 現行 README で初回合格 | 説明を補った README で初回合格 | 提出後に独立して確認したこと |
| --- | ---: | ---: | --- |
| 配送ラベル | 2/2 | 2/2 | JS から元の TS オブジェクトを渡せる。空文字・日本語の便名を扱え、補助関数は非公開。生成した型定義も元の Shipment を使う。 |
| 波形の二乗和 | 2/2 | 2/2 | 空・ゼロ・正負混在・小数の入力で両関数が正しい。JS は Float32Array を受け、Wasm の公開関数に energy があり、has_signal は JS 側にある。 |

各ラウンドは履歴を共有しない新規エージェント 4 人で実行しました。課題、コンパイラ、コンパイル上限は同じで、2 周目は README だけを変更しました。別の採点者に条件を伏せて成果物と検証記録を渡したところ、機能・公開境界・利用経路は全件各 2 点（計 6 点）でした。採点外・失敗は 0 件です。[試行別の採点台帳](ledger.json)

## 配送ラベルで迷ったのは空の括弧

現行版の 2 人とも、文字列を持つタグは `Shipped(code)` と書けた一方、タグしかない状態を `Waiting` と書くか `Waiting()` と書くか迷いました。どちらも別の節の enum の例を手がかりに解決しています。うち 1 人は型取り込みの節が「プレーンなレコード型だけ」から始まるため、判別 union を渡せるかも一度疑っています。[現行版の提出 1](rounds/01/status-1.json)・[提出 2](rounds/01/status-2.json)

2 周目では、受け取れる型を節の冒頭に並べ、タグだけの `Idle` とデータ付きの `Busy(n)` を同じ match 式に置きました。2 人ともその例で括弧の疑問が解けたと報告しました。両者に残った要望は例の位置です。**型取り込みの節の冒頭で、TS の型定義のすぐ下に対応する match を置く**のが次の変更候補です。[比較版の提出 1](rounds/02/status-1.json)・[提出 2](rounds/02/status-2.json)

## Wasm で探したのは JS 側の呼び出し方

現行版の 2 人とも、数値計算は書けたものの、JS 側で Wasm を手動初期化する必要があるか迷いました。最終的には生成 JS を通常の ES モジュールとして import し、値を渡すだけで動くことを自分で確認しています。[現行版の提出 1](rounds/01/energy-1.json)・[提出 2](rounds/01/energy-2.json)

2 周目では、生成したモジュールを読み込んで関数を呼ぶ Node.js の例を `@wasm fn` の節に加えました。2 人とも呼び出し方を資料内で確認できました。1 人は「Node.js」で検索して例に到達し、冒頭の生成ファイル一覧からのリンクを希望しています。もう 1 人は `F32Array` の節に、合計を `let mut sum: f32 = 0.0` と宣言する例が欲しいと報告しました。**最初に足すなら、言語側の関数と JS 側の import を対にした例へのリンク**です。[比較版の提出 1](rounds/02/energy-1.json)・[提出 2](rounds/02/energy-2.json)

今回の比較では、資料を補う前から全員が正しいコードを書けていました。確認できた変化は、疑問への答えを同じ節で見つけたという本人の報告です。人間の利用者での再現性、探索にかかった時間、未出の課題への効果は未測定です。変更した資料は評価用の [README 差分](guide.patch) として残しています。
