# リージョン (ライフタイム) 検査、その 12: 共有の deref、クロージャの逃げ出しと再借用、注釈のあるパターン、impl のシグネチャ (issue #1)

日付: 2026-11-22

その 11 ([2026-11-22-08](2026-11-22-08-region-check-11.md)) は #54 でマージした。この段階では、tests/ui で受け入れて
いたケースをさらに扱う。その多くはクロージャのものである: クロージャの本体がキャプチャしたものの何を返し、何を
しまえるか、クロージャの呼び出しが引数を評価する間に何を持つか、トレイトオブジェクトのために作ったクロージャを
どのシグネチャで検査するか。また、impl のメソッドをトレイトの宣言とリージョンで比べる。

## 1. 加えたもの

### 借用検査

- **`DerefMut` のない `Deref` が届く先は共有である。** `*rc = 3`、それを通して届くフィールド (`rc.y = 1`)、それを
  通して呼ぶ `&mut self` のメソッド (`Rc<Vec<u8>>` での `rc.push(1)`) は共有のデータに書いていた: これらは E0594 /
  E0596 である (borrowck/borrowck-borrow-overloaded-deref.rs、-auto-deref.rs)。借用検査はそのような deref を `&` と
  同じように追う。deref を通して書く prelude の `MutexGuard` は除く。
- **キャプチャした `&mut` を再借用するクロージャは `*x` を借用する。** `&mut` が期待される所に渡す `&mut` の
  キャプチャ (`|| foo(x)`、`|| s.put(x)`) は、`|| foo(&mut *x)` と同じく `*x` の一意な借用である。そのクロージャは
  `FnMut` なので、`mut` でない束縛を通して呼ぶと E0596 になる (closures/issue-81700-mut-borrow.rs)。クロージャが
  引数として渡す `&mut` は `*x` を借用する。`look(x)` なら共有、`foo(x)` なら一意である。クロージャが生きている間の
  `*x` の借用は衝突する (E0500 / E0502)。以前は、クロージャはコピーを持ち、ローンを持たなかった。
- **インスタンスがどれも `Copy` の型を使うジェネリックな関数も、プレースホルダでムーブを検査する。**
  `dup(1u32)` としてしか呼ばない `fn dup<T>(x: T) -> (T, T) { (x, x) }` を受け入れていた: 借用検査はインスタンスの
  上で行い、そこでは x は `Copy` である。境界が `Copy` にしない型パラメータに、どのインスタンスも `Copy` の型を
  与えるとき、本体を (呼ばれないジェネリック関数と同じく) プレースホルダでもう一度検査する。そこでは T をムーブする
  ことが引き起こすもの (E0382、E0505、E0507) だけを報告する。残りはインスタンスが検査した。
- **呼び出すクロージャは、借用しているものを、引数の後の呼び出しまで持つ。** `(|x| f(x))(call_rec(f))` と
  `let c = |x| v.len() + x; c(take(v))` を受け入れていた (regions/region-bound-on-closure-outlives-call.rs、E0505)。
  呼ばれる側は引数より前に読まれ、クロージャが借用しているものは引数を評価する間保たれていなかった。rustc の呼び出しの
  `&c` / `&mut c` と同じく、呼ばれる側が持つものを、呼び出しが終わるまで呼び出しの一時値が持つようにした。
- **値で持つクロージャのキャプチャは、本体の呼び出しより長く生きる。** `move || { b = Some(&a); }` を受け入れていた
  (borrowck/borrowed-data-escapes-closure-148392.rs、rustc の E0521)。値で持つキャプチャは、借用検査にとって本体の
  ローカルであり、本体とともに消えていた。それはクロージャの環境の中で生き続けるので、本体の終わりで、そのような
  キャプチャが持つものは本体から逃げ出す。本体自身のデータ (値で持つほかのキャプチャ、ローカル) のローンは
  「does not live long enough」になる。
- **種類が何にも決まらないクロージャが、参照でキャプチャしたものを変えるクロージャを返す。**
  `|| { || { x.push(()) } }` を受け入れていた (nll/issue-40510-3.rs、closures/nested-closure-escape-borrow.rs):
  「captured variable cannot escape `FnMut` closure body」。クロージャを作る関数は、境界も期待する型もその種類を
  決めないとき、そのクロージャに印を付ける。そのような本体では、クロージャが参照でキャプチャしたものの可変の
  ローンを持つ値を返すと報告する。境界が種類を決める所に渡すクロージャ (`FnOnce` での `once(|| || w.push(2))`) は
  報告しない。
- **`move` クロージャは、値で持つキャプチャが持つものを持つ。** `move || { vec.clear(); let mut iter = vec.iter();
  move || iter.next() }` を受け入れていた
  (borrowck/do-not-suggest-adding-move-when-closure-is-already-marked-as-move.rs): 内側のクロージャの値は、参照で
  キャプチャしたもののローンしか持っていなかった。

### リージョン

- **型注釈のある分解する `let` は、注釈の型の値から束縛する。** `let (ref y, _z): (&'a u32, u32) = (&22, 44); *y` を
  `&'static u32` として返すのを受け入れていた (nll/issue-55401.rs): パターンは、注釈のでなく初期化式の木から束縛して
  いた。今は (`let _: T = ..` と同じく) 初期化式が注釈の型へ流れ、型が一致するとき、パターンはその木から束縛する。
- **クロージャのトレイトのトレイトオブジェクトが期待される所で作るクロージャは、そのシグネチャで検査する。**
  `&mut dyn FnMut(&isize)` に対する `with_int(&mut |y| x = Some(y))` と、
  `let f: &mut dyn FnMut(&isize) = &mut |y| x = Some(y);` を受け入れていた
  (borrowck/regions-escape-unboxed-closure.rs、E0521)。本体を検査するリージョンのシグネチャをクロージャに与えるのは、
  ジェネリックな境界だけだった。今はトレイトオブジェクトの文面がその境界であり、その名前のあるライフタイムは
  クロージャの外のものである。
- **リージョンのためにトレイトの宣言より一般的でない impl のメソッド。**
  `fn foo<'a>(x: &i32, y: &'a i32) -> &'a i32` に対する `fn foo<'a>(x: &'a i32, y: &'a i32) -> &'a i32` と、
  `fn bar(&self, r: &mut Re)` に対する `fn bar<'a, 'b>(&'a self, _r: &'b mut Re<'a>)` を受け入れていた
  (lifetimes/lifetime-mismatch-between-trait-and-impl.rs、trait-impl-mismatch-elided-lifetime-issue-65866.rs):
  「`impl` item signature doesn't match `trait` item signature」。宣言のリージョンは普遍的で、impl のメソッド自身の
  ライフタイムと省略したリージョンは変数である。宣言の各引数は impl の引数へ流れ、impl の結果は宣言の結果へ流れる
  (変性つき)。それからリージョンのソルバが、宣言のリージョンのうち、そうと知られていない別のリージョンより長く
  生きなければならないものを報告する。3 種類のシグネチャは比べない: impl やトレイト自身のライフタイムを名指しする
  もの、ライフタイムの間に境界のあるもの、両側で引数のリージョンの数が違うもの (`Self`、トレイトの型パラメータ)。

## 4. レビュー (CodeRabbit、rustc 1.97 で確かめた)

CodeRabbit は #64 を 3 回レビューした。指摘はどれも rustc 1.97 で確かめた。1 回目は 8 つの指摘で、6 つは当たって
いて、直してテストした (`part12_review`):

- **親が lower されないとき、クロージャの本体は親の lower が伝えたことを失っていた。** 関数の lower は、それが作る
  クロージャに、その種類を何も決めないこと (`Insts::kind_free`) を伝え、いくつかにはリージョンのシグネチャ
  (`Insts::closure_rg`) を与える。どちらもプロセスの `Insts` にしかなかった。キャッシュから、セッションの検査の
  記録から、または並列ビルドの子プロセスから得た親はそこで lower されず、そのクロージャはそれらなしで検査されて
  いた: セッションの 2 回目の検査は `|| { || { x.push(()) } }` を受け入れていた。今はこれらは親の Blob と
  インスタンスの記録とともに保たれ、読み戻すと `Insts` に渡る。リージョンのシグネチャは、この作業の前から同じ
  ように失われていた。
- **ターゲットが自分自身の型である `Deref`** (`impl Deref for S { type Target = S; .. }` の後の `|| s.missing`)
  で、借用検査は deref を永遠に追っていた。上限で止める (2 回目から 128)。
- **注釈が `'static` を書く分解する `let`** は、その前に何もリージョン検査を有効にしていないとき、それを有効に
  しなかった: `let (a, _): (&'static i32, u8) = (&x, 0);` を受け入れていた。`let _: &'static T = ..` と同じく
  検査を有効にする。
- **穴のある注釈** (`let (x, _): (&'static u8, _) = (r, 0u8);`) は、型が注釈のと違う初期化式と関係づけられて
  いなかった。今はタプルの注釈を要素ごとに関係づけ、`_` は初期化式の要素を取る。
- **自分をムーブする引数で呼ぶクロージャ** (`String` を持つ `move` クロージャでの `c(drop(c))`) を受け入れて
  いた: 呼び出しは、クロージャのキャプチャが借用するものしか持っていなかった。クロージャ自身の借用も持つ
  (E0505)。`e(e(1))` は今も受け入れる。
- **`&'static` と書いた impl の引数** は、impl の省略した結果にライフタイムを与えるときに除かれ、比較はそこで
  止まっていた: トレイトの `fn f(x: &u8) -> &u8` に対する `fn f(x: &'static u8) -> &u8` を受け入れていた。今は
  E0308 である。

2 つは当たっていなかった:

- `move || { b.push(&a); drop(b); }` は rustc でも E0597 である。`b` の型はクロージャの外のリージョンを名指し
  するので、本体がその後 `b` をどうしても、クロージャ自身の `a` のコピーの借用をそこにしまうことはできない。
- `Rc<T>` での `B::go(&rc)` は rustc で E0277 である: トレイトのパスを通した呼び出しは引数を deref しない。
  正しい `B::go(&*rc)` は main でも拒否する。それは 2 つのトレイトの `go` という名前のメソッドの間の選択による
  もので、`Deref` を通した書き込みの新しい検査によるものではない (5 節)。

2 回目は、それらの修正への 2 つの指摘で、どちらも当たっていて、直してテストした (`part12_review_2`):

- **16 個より多い `Deref` を通した書き込み。** deref の上限のため、借用検査は 16 個を越えるとその場所を飛ばしていた。
  そのため、`DerefMut` のない 17 個の `Deref` の impl を通した `x.field = 1` を受け入れていた (rustc では E0594)。
  今は rustc の既定の再帰の上限 (128) まで deref を追う。それを越えると rustc 自身がプログラムを拒否する (E0055)。
- **分解する `let` の初期化式の中の呼び出し** (`let (_x, _): (&'static u8, u8) = (id(r), 0);`) は、注釈の
  `'static` が検査を有効にする前に lower されていた。そのため呼び出しは木を持たず、プログラムを受け入れていた。
  今は初期化式を lower する前に検査を有効にする。

3 回目は 2 つの指摘で、どちらも当たっていて、直してテストした (`part12_review_3`):

- **128 個を越える `Deref`。** 借用検査はその場所を飛ばし、lower は連なりを追っていた。そのため、129 個の共有の
  `Deref` を通した書き込みを受け入れていた。rustc はそのようなプログラムを拒否する (「reached the recursion
  limit」)。今は、`Deref` の連なりが 128 歩 (rustc の既定の再帰の上限) のうちにフィールドへ届かないフィールド
  アクセスは E0055 である。循環も、それほど長い連なりも含み、ジェネリックなターゲット (`W<T>: Deref<Target = T>`)
  を通るものも含む。これを確かめると、2 つの型を通した循環 (`A` から `B`、`A` へ) が型推論で zustc の
  スタックをあふれさせていた (main でも)。型推論も同じだけ連なりを追い、その循環は E0055 になる。
- **クロージャの中の明示的な `return` や `?`** は、値で持つキャプチャの逃げ出しの検査なしに本体を出ていた。そのため
  `move || { b = Some(&a); return; }` を受け入れていた (rustc では E0521)。今は本体の出口ごとに検査する。

#54 のレビューへの、マージ後のフォローアップも当たっていた: #54 から、ブランケット impl の境界は 8 つの impl の
深さまでしか追わなかった。そのため、`()` が最初のトレイトを持ち、rustc が受け入れるのに、10 個のブランケット impl の
連なりを通した `().go()` を拒否していた。今は、途中で再び出会ったトレイト (ブランケット impl の循環) か、rustc の
既定の再帰の上限 (128) を越えた連なりで止める。各トレイトの答えは保つので、多くのトレイトの連なりもトレイトごとに 1 回だけ
追う (`blanket_chain_past_eight`)。

## 5. まだ扱っていないもの

- **メッセージ。** 上のケースのいくつかは、rustc のでなく zustc 自身の言葉で報告する: `move` クロージャの逃げ出しは、
  rustc が E0521 と言う所で「does not live long enough」であり、可変で持つキャプチャを引数がムーブするクロージャの
  呼び出しは、rustc が E0505 と言う所で「cannot use `v` because it was mutably borrowed」である。行は rustc と同じ。
- **impl のメソッドとトレイト** は、どちらも impl やトレイト自身のライフタイムを名指ししないとき (impl のヘッダを
  通した両者の関係は保っていない)、そして両側で同じ数のリージョンを持つ引数についてだけ比べる:
  トレイトの `To` がヘッダの `&ProofReader` である `impl HaveRelationship<&ProofReader> for Article`
  (traits/param-without-lifetime-constraint.rs) は比べない。
- **`FnMut` を通したクロージャの逃げ出し** は、本体が返すクロージャと、本体の終わりで値で持つキャプチャが持つものに
  ついて追う。返す値の中で関数に渡すクロージャ (`flat_map` のクロージャから返す `.map(|c| .. s ..)`:
  borrowck/issue-95079-missing-move-in-nested-closure.rs) は追わない。
- **型パラメータを文面に持つ `dyn Fn` (`dyn Fn(T)`)** のために作るクロージャには、そのシグネチャを与えない。
- **別のトレイトもその型に与えるメソッドへの、トレイトのパスを通した呼び出し** (`A::go(&mut self)` も実装する
  ときの `B::go(&*rc)`) は、型の不一致として拒否する: トレイトのパスが決める前に、メソッドを名前で選ぶ。この作業の
  前からそうだった。
- **`#![recursion_limit]`** は読まない: `Deref` の連なりとブランケット impl の境界は、rustc の既定の上限 (128) まで
  追う。上限を上げ、それより長い連なりを要するクレートは拒否する。
