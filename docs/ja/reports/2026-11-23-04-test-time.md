# テストの時間: どこにかかっていたか、何を削ったか、nextest のような `zurgo test`

Date: 2026-11-23

## 時間がかかっていたところ

CI の test ジョブ (run 638、7a38644) は 9 分 50 秒かかっていた。

| ステップ | 時間 |
|---|---|
| wild と valgrind を入れる | 5 分 21 秒 (valgrind の 27 MB を 94 kB/s のミラーから取った: 4 分 46 秒) |
| `cargo build --release --workspace` | 52 秒 |
| `cargo test --release --workspace` | 2 分 05 秒 (テストのターゲットのビルドが 24 秒、実行が約 100 秒) |
| `tests/compare.sh` | 22 秒 |
| formal/connect | 51 秒 (依存を毎回ビルドしていた: rust-cache が残していなかった) |

テストの時間は、それぞれ数百のプログラムを 1 つずつ順にビルドして動かす、少数のテストに集まっていた (ローカル、4 コア)。

| テスト | 時間 |
|---|---|
| `driver2_cranelift` | 44.3 秒 |
| `security` | 27.4 秒 (そのうち valgrind が約 20 秒) |
| `driver2_inline` | 17.8 秒 |
| `driver2`、`wasm` | それぞれ 8.7 秒 |
| `ast_codegen` | 7.1 秒 |
| `zurgo` | 6.3 秒 |

`cargo test` はテストのバイナリも 1 つずつ順に動かすので、長いテストが 1 つあるバイナリの間、ほかのコアは空く。

ビルド: zust-syntax の release ビルドは単独で 11.9 秒、そのうち LLVM が約 10 秒、クレート内の ThinLTO (`lto = false` で
codegen unit 16) が 4.8 秒。クリティカルパスは base/ir → syntax → sema → typeck → core → zurgo。

## 変えたこと

- 順に回すループに `tests/common/par.rs` (`par_map`、コアに仕事を配るキュー): `driver2_cranelift` 44 → 12 秒、
  `driver2_inline` 18 → 5 秒、`driver2` 9 → 3 秒、`ast_codegen` 7 → 2 秒、zurgo の registry の 2 つのテストがそれぞれ 5 → 2 秒。
  出力はソースのディレクトリごとのディレクトリに置く (`floats.rs` と `modules.rs` は 2 つのディレクトリにある)。
- `security.rs`: `//@ args` のあるケースは、すべての実行ではなく終了コードごとに 1 回 (0 で終わる最初の実行、panic する
  最初の実行) だけ valgrind で動かす: 27 → 15 秒。`ZUST_SECURITY_VALGRIND=all` ならすべて動かす。2 つの `todo(valgrind)`
  のリークは今も捕まる (隠れたら「passes now」でテストが失敗する)。実行の多いケースから始める。
- `tests/compare.sh`: 例ごとに別のプロセスで、すべてのコアで: 30 → 9 秒。
- CI に cargo-nextest (`.config/nextest.toml`、`--profile ci`): 4 コアで全体が 71 → 50 秒 (上の変更の後の `cargo test` と
  比べて)。その 50 秒の間 4 コアは埋まっている (CPU 190 秒) ので、順番ではこれ以上縮まない: 長いテストに nextest の
  `priority` を付けても変わらなかった (53 秒)。
- CI の test ジョブ: valgrind のパッケージをキャッシュし、ワークスペースのビルドの間にバックグラウンドで
  (`--no-install-recommends` で) 入れる。rust-cache が formal/connect の依存も残す。`CARGO_PROFILE_RELEASE_LTO=off`。

ThinLTO の損得 (ローカルで測った):

| | release (今のまま) | `lto = "off"` |
|---|---|---|
| テストのクリーンビルド | 162 秒 | 87 秒 |

テストの時間の合計は `cargo test` で 148 秒 → 83 秒、nextest ならテスト全体が 50 秒。

## nextest のような `zurgo test`

zurgo にはまだ `test` がなく、zustc にも `--test` がない。nextest のモデル (バイナリごとにテストを列挙し、テストごとに
別のプロセスで動かし、全部をコアに配る) は、libtest のモデルより zustc に合う。

- ハーネスが小さい。テストを列挙する (`--list --format terse`。libtest の取り決めなので nextest も読める) ことと、名前の
  テストを 1 つ動かす (`--exact <name>`) ことだけでよい。panic は 101 で終わり、`Err` を返す `Result` のテストは 1 で
  終わる: プログラムの側に `catch_unwind` もスレッドも出力の捕捉もいらない。`#[test]`・`#[should_panic]`・`Result` の
  テストを持つ `mod tests` に、そういうハーネスを手で書くと、今の zustc でビルドでき (`#[cfg(test)]` は外して:
  zustc にはまだ `--cfg` がない)、そのとおりに動く。
- `should_panic(expected = ..)`、`#[ignore]`、タイムアウト、再試行、出力の捕捉はランナー (zurgo) の仕事で、すべての
  バイナリに 1 度書けばよい。

要るもの:

1. zustc: `--cfg test` (と `--cfg` 一般)。`--test`: `#[cfg(test)]` のアイテムを残し、`#[test]` の関数 (パス、`#[ignore]`、
   `#[should_panic]`) を集め、ハーネスの `main` を足す。panic のメッセージは `src/main.rs` ではなくソースのファイルを
   指すべき。
2. zurgo: `test`。テストのターゲット (lib の単体テスト、lib に対する `tests/*.rs`、bin の単体テスト) を dev-dependencies
   込みでビルドし、それぞれを列挙し、すべての (バイナリ、テスト) の組を `-j` のワーカーで動かす: libtest のフィルタ
   (`<filter>`、`--exact`、`--ignored`、`--include-ignored`、`--skip`)、`--no-fail-fast`、遅い・止まったテストの
   タイムアウト、失敗したテストの出力、時間つきのまとめ。doc テストは最初は対象にしない。
3. nextest の一歩先: zurgo はテストごとに前回の時間を残し (`target/zust/test-times`)、長いものから始める。長いテストの数より
   コアが多いマシンで効く: 最後に始めた長いテストが、終わりに 1 つだけで動くことがなくなる。

得られるもの: cratebench のクレートに `zurgo test` (それらの単体テストは、`run` の次に zustc を確かめるもの)、rustc の
tests/ui のうち `compile-flags: --test` の 98 個 (そのうち 86 個に `#[test]` がある)。このリポジトリのテストを速くする
ものではなく (zustc はそれらをビルドしない)、それ自体が 1 つの機能。
