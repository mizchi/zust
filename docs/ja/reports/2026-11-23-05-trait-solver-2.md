## E0119: 衝突する impl

`Coherence.lean` に `conflict_sound` を足した: ある代入で 2 つの impl の頭が等しくなり、そこで solver が両方の where 節を
証明すれば、両方が 1 つのゴールに当てはまる (本物の衝突)。`TraitDb::conflict` はこれに従う:

- 2 つの頭 (self 型とトレイト引数。2 つめの impl のパラメータは付け替える) の一階の単一化 (出現検査つき)。頭は線形でなくて
  よい (`impl<T> From<T> for T`)。代入した頭が等しいことをその後で比べる: 定理の仮定を信じずに確かめる;
- 共通のインスタンスでの where 節は *strict* モードで証明する。読めないものを落とすと `yes` は出やすくなる。その 1 は `no` の
  ためにそれを使ったが、衝突では偽の衝突を作ってしまう。なので strict モードでは、`yes` は zustc がすべて読めた impl
  (`Clause::exact`。さらに driver がヘッダの文字列から where 節がすべてパラメータへのものであることを確かめる: 要約はそれ以外を
  跡を残さず落とす) からのものだけ、std のトレイトは `implements` が正確なところだけ、整数リテラルの寛容さもなし;
- `Ty` が区別できないものは「分からない」: 参照を含む関数ポインタ (ライフタイムは消えているので `for<'a> fn(&'a u8)` と
  `fn(&'static u8)` は同じ `Ty`)、トレイトオブジェクト (`dyn Error + 'a` と `dyn Error + Send + 'a` は同じ `Ty`。thiserror には
  両方への impl があり、zurgo の registry テストが見つけた)、unsized な型に束縛されるパラメータ (`?Sized` は要約にない)。

strict モードとこの 2 つの規則なしの最初の実行では退行が 4 つ (coherence-fn-inputs など) あり、1 件は自分の理由でない理由で
「通って」いた (traits/trivial-unsized-projection-in-coherence.rs。落とした where 節のため。いまは正しく通らない)。どちらも下の数字の前に直した。

## E0277: impl のスーパートレイト

`trait Complete: Partial` と `trait Partial: Copy` での `impl<T> Complete for T` は `T: Partial` と `T: Copy` が要る
(`Obligations.lean`: impl のパラメータを rigid にし、その where 節を環境にする)。driver はプログラムのトレイトの impl を
すべて、そのスーパートレイト全部 (上までたどる) について、impl のパラメータを境界が環境のすべてであるプレースホルダにして
確かめる (`holds_rigid`)。

## `dyn Trait<A>` への型強制での E0277

`to_dyn` はトレイトの名前しか見ていなかった。いまはトレイト引数つきで solver に聞く: `impl Trait<&str> for Struct` しか
ないとき `Struct` から `dyn Trait<isize>` は E0277。

## トレイト引数による impl の選択

`impl Conv<u64> for u8` と `impl Conv<bool> for u8`: レシーバはどちらにも合い、zustc は最初のものを呼んでいた。メソッド探索は
いま solver の頭のマッチングと同じ選び方をする: 呼び出しが持つべき型を返すメソッドの impl。境界経由
(`fn conv_to<T, S: Conv<T>>`) でも、直接・明示の呼び出し (`3u8.conv()`、`Conv::conv(&5u8)`、`<u8 as Conv<bool>>::conv(&0u8)`)
でも。`examples/trait_solver.rs` がこれらを rustc の出力と比べる。

## auto trait: 余帰納的

`Coinductive.lean` に `csolve` (一周して戻ってきたゴールを成り立つと数える solver) を足し、最大不動点に対して証明した:
`csolve_yes_sound` (`yes` のゴールは無矛盾なゴールの集合に入る) と `csolve_no_sound`。例: `struct List { next:
Option<Box<List>> }` は `csolve` では `Send`、`solve` ではそうでない。

zustc の `Send` / `Sync` は構造的 (`Program::auto_trait`) で、型パラメータはすべてこれを持っていた。いま (`Cx::auto_goal`):

- 構造の規則を節として `csolve` と同じように解く: 構造体はフィールドで、一周して戻った型は成り立つ、`&T: Send` は `T: Sync`
  が要る、`Arc<T>` は `T: Send + Sync`、`Mutex<T>: Sync` は `T: Send`、`Rc` はどちらでもない、`Cell` / `RefCell` は `Sync`
  でない;
- 型パラメータは境界によってだけ auto trait を持つ (プログラムのトレイトのスーパートレイトを通して)。要約は `Send` / `Sync` の
  スーパートレイトを落とすので、driver がトレイトのヘッダから読む (`trait Foo: Send`、`where Self: Sync`)。zustc の知らない
  境界 (スーパートレイトを持っていない std のトレイト) は「分からない」;
- `fn f<S: Sync>(s: S)` の中の `is_send(s)` は E0277 (`` `S` cannot be sent between threads safely ``)。S が何でも成り立つので、
  どこからも呼ばれないジェネリック関数からも報告する;
- `trait Foo: Send` の impl は self 型が Send であることが要る。

## 残っているもの

- 関連型: 関連型への where 節 (`where <T as Mirror>::Mirror: Foo`) は impl の節からまだ落とす。正規化はモデル化していない。
- std の impl との E0119 (`impl<S> Into<S> for GenX<S>` は std のブランケット `Into` と衝突する): std の impl は節でない。
- impl の頭のライフタイム (関数ポインタの E0119、高階の境界) は `Ty` にライフタイムが要る。
- メッセージのプレースホルダの名前が zustc のもの (`impl Sync` が `__impl0`、モジュールの中のトレイトが `a__b__Hidden`)。
