# zurgo M0: Cargo のパッケージを zustc でビルドする

日付: 2026-11-21

zustc には Cargo のパッケージをビルドする手段がなかった: そのワークスペースのビルドは、手で書いたクレートの一覧を
受け取る。これは mizchi/zust#28 の最初のマイルストーンである。Cargo と互換のドライバ `crates/zurgo` を足す (最初は
zargo という名前だったが、そのクレート名は crates.io で使われている)。zurgo は Cargo.toml と Cargo.lock を読み、
ソースを見つけ、cargo と同じように feature を有効にし、そのグラフを同じプロセスの中で zustc のワークスペースの
ビルドでビルドする。`zurgo metadata` は `cargo metadata` の JSON を書く。proc macro の issue、mizchi/zust#29 も同時に
書いた。使い方: [zurgo.md](../zurgo.md)。

## 1. 何でできているか

3,100 行で、crates.io への依存はない (serde_json はテストだけ):

| モジュール | 行 | 中身 |
|---|---:|---|
| `toml.rs` | 529 | TOML: テーブル、テーブルの配列、ドットと引用符のキー、インラインのテーブル、4 種類の文字列、数、日付 |
| `resolve.rs` | 592 | Cargo.lock とマニフェストからのパッケージのグラフと、feature の有効化 |
| `manifest.rs` | 381 | Cargo.toml: Cargo の自動の発見を含むターゲット、3 種類の依存と `[target]` の下のもの、feature、ワークスペースからの継承 |
| `metadata.rs` | 258 | `cargo metadata` の JSON |
| `semver.rs` | 244 | 版と要求。`^`、`~`、ワイルドカード、プレリリースは Cargo の規則で |
| `platform.rs` | 223 | `cfg(..)` のプラットフォームのキー。値は x86-64 Linux と wasm32 で `rustc --print cfg` が出すもの |
| `compile.rs` | 217 | zustc のワークスペース (`CrateSpec`) とビルド |
| `lock.rs`、`json.rs` | 354 | Cargo.lock と、cargo のレジストリの index のキャッシュ |

zust-core はフィールド 1 つだけ変わる: `CrateSpec::exe`、バイナリの実行ファイルの名前である。パッケージの
ライブラリとバイナリはパッケージの名前を共有し、zustc はクレートのファイルをその名前で名付けるので、zurgo は
バイナリに別のクレート名を付け、実行ファイルの名前をここに持たせる。

## 2. cargo metadata に合わせる

テストは、テストのパッケージと、cratebench/ui の dioxus (344 パッケージ) と leptos (180) のアプリについて、
`zurgo metadata` と `cargo metadata` を比べる。プラットフォームの絞り込みなしと、wasm32 と x86-64 Linux の
`--filter-platform` とで比べる。比べるのは、パッケージ、id、ターゲット、有効な feature、辺とその `dep_kinds` である。
どこでも同じになる。

最初の版は cargo の feature のリゾルバの、文書にある規則に従っていて、4 つの点で違った。どれも `cargo metadata` が
何を出すかについて、何かを示した:

- **`cargo metadata` が出すのは依存のリゾルバのグラフで、feature のリゾルバのものではない。** その feature は、
  すべての種類、すべてのプラットフォームにわたってまとめられる。弱い `dep?/feat` も `dep` をグラフに入れる: toml の
  `std = ["serde_core?/std", ..]` は、toml の `serde` feature が無効でも、toml から serde_core への辺を作る。
  `zurgo build` は、cargo がビルドに使う feature のリゾルバの規則のままにする: ホストの側、dev-dependencies なし、
  プラットフォームの確認、待つ弱い feature。
- **`--filter-platform` は辺を絞るだけである。** 辺は、その宣言のどれかが当てはまれば出され、その `dep_kinds` には
  すべての宣言が並ぶ。ほかのプラットフォームのものも並ぶ。wasm32 の絞り込みでも、dioxus-logger の
  tracing-subscriber の種類には `cfg(not(target_arch = "wasm32"))` があり、tracing-subscriber の feature には、
  その宣言だけが求める `fmt` がある。
- **`x/f` は、`x` という名前の feature も有効にする。** `x` が optional の依存で、その名前の feature (明示のものか
  暗黙のもの) があるときである。yoke には `zerofrom = ["dep:zerofrom"]` と `derive = [.., "zerofrom/derive"]` が
  あるので、`derive` は `zerofrom` feature を有効にする。
- **ダウンロードされていないパッケージも数に入る。** `cargo metadata --filter-platform` と `cargo fetch --target` は、
  ほかのプラットフォームのパッケージを取ってこない: ここでは dioxus のグラフの 344 のうち 49 がダウンロードされて
  いなかった (windows-sys、rustix、ndk など)。それでもその依存は、共有のパッケージの feature を有効にしうる:
  bitflags の `std` はそれらからだけ来る。cargo はその依存と feature をレジストリの index のキャッシュ
  (`registry/index/*/.cache`。項目ごとに版と JSON の 1 行) に持っていて、zurgo はそこから読む。また cargo は
  プラットフォームのキーを、その構文解析から出し直す (`cfg(target_os="hermit")` は `cfg(target_os = "hermit")` に
  なる)。zurgo も同じようにする。

dioxus では、`zurgo metadata` は 39 ms、`cargo metadata --offline` は 320 ms かかる。`cratebench/ui/run.py` は今は
グラフを zurgo から読み、cargo はダウンロード (`cargo fetch`) にだけ使う。その出力は前と同じである。

## 3. ビルド

- path のワークスペースは、その cargo のビルドと同じようにビルドされ、動く:
  - 1 つの名前のライブラリとバイナリ;
  - `default`、依存の `features = [..]`、`dep:` を通した feature;
  - コンパイルできない dev-dependency。これはビルドしてはいけない。

  同じビルドをもう一度すると何もしない: どのクレートも新しいままで、何もリンクしない。
- crates.io の cratebench の 6 つのクレート (fnv、adler2、hex、itoa、rustc-hash、cfg-if) は、それぞれ cratebench の
  アプリと一緒に、その cargo のビルドと同じものを出す。
- dioxus と leptos のアプリでは、`zurgo build` は最初に届いた proc-macro の依存で止まり、それを
  (`const_format_proc_macros`、`futures-macro`) mizchi/zust#29 と一緒に示す。

hex は、その cargo のビルドと同じものを出さなかった: `<[u8; 4]>::from_hex(..)` がエラーを返した。これは zurgo の
せいではなかった: cratebench の hex をそのまま `zustc build` しても同じものを出した。二分探索で 61ae81a
("pick_overload finds the group of a suffixed candidate") が見つかった:

- `[u8; 4]` と `[u8; 2]` への 1 つの trait の impl は、同じ名前の関数 `n` と `n#1` を作り、それらは 1 つの
  オーバーロードの組に入る。
- 呼ぶ側は self の型でその 1 つを選ぶ。61ae81a の前は、pick_overload は接尾辞の付いた `n#1` の組を見つけなかった
  ので、その選択がそのまま残った。
- それ以後は、最初の引数で選び直していた。`fn from_hex<T: AsRef<[u8]>>(hex: T)` ではどの候補も合うので、最初の
  impl が呼ばれていた。
- 今は、`self` のない関数を、ほかの self の型の impl の中から選び直さない: その最初の引数は self の型について何も
  言わない。1 つの self の型のオーバーロード (1 つの型への `From<&str>` と `From<String>`) は、今も引数で選ぶ。
- `tests/probe/assoc_fn_by_self_type.rs` がその両方を確かめる。

cratebench の出力を比べる CI のジョブはない (KPI のジョブはその時間を測る) ので、これは 1 日気づかれなかった。今は
zurgo のテストがそれを比べる。

## 4. 変えなかったもの

`cratebench/run.py` は今も `zustc build` と手で書いたワークスペースでビルドする。KPI のジョブ
(`bench/kpi_track.py`) は cratebench のビルドをそれで測っていて、zurgo を通すとその KPI が測るものが変わる。同じ
クレートは、zurgo のテストで zurgo を通してビルドする。

## 5. M1 に残すもの (mizchi/zust#28)

- **ビルドスクリプト。** まだ実行しない。それぞれを警告で示す。
- **zustc のワークスペース:**
  - extern の名前と分けたクレートの名前。1 つのクレートの 2 つの版と、名前を変えた依存のため;
  - クレートごとの edition;
  - `env!` / `option_env!`;
  - wasm32。
- **zurgo 自身:**
  - 自前のリゾルバ;
  - ダウンロード;
  - git の依存;
  - `[patch]`。
