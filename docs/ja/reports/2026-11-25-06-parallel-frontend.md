# スレッドで動くフロントエンド: rustc の並列フロントエンド、zustc の現状、プロトタイプ、設計

Date: 2026-11-25

rustc の nightly は `nightly-2026-11-14` から、フロントエンドを既定でスレッドで動かしている
([ブログ](https://blog.rust-lang.org/2026/11/16/enabling-parallel-frontend-on-nightly/))。既定は 2 スレッドで、
`-Zunstable-options --jobs-frontend=N` で増やせる。ブログによると、`check` ビルドの壁時計時間の平均の変化は 2 / 4 / 8
スレッドで −22% / −38% / −44% である。このレポートでは、zustc のフロントエンドを今後何を前提に設計すべきかを考える。
扱うのは次の 4 つ:

1. rustc がどうしているか (ソースから読んだもの)
2. zustc がすでにしていること
3. zustc の並列の部分をスレッドで動かすプロトタイプと、その計測
4. そこから導いた設計と、作業の順番

## 1. rustc の並列フロントエンド (ソースから)

rust-lang/rust の 8d773821 (2026-11-25) の clone から読んだ。パスは `compiler/` の下。

- **スレッドプール。** `rustc_thread_pool` は rustc 用の rayon-core の fork で、次の 4 つを加えている:
  - デッドロックハンドラ。動いているワーカーがなく、待っているワーカーがあるときに呼ばれる
  - `mark_blocked_and_wait`。他のスレッドのクエリを待つスレッドが使う
  - jobserver のフック。待っているワーカーや眠っているワーカーはトークンを返す
  - `tlv`。各ジョブが運ぶ 1 つのスレッドローカルなポインタ。rustc の `ImplicitCtxt` (`TyCtxt` と今のクエリ) は、これで
    盗まれた仕事についていく

  プールは `rustc_interface/src/util.rs` (`run_in_thread_pool_with_globals`) で、17 MiB のスタックで作られる。既定の 2
  スレッドは rustc ではなく bootstrap が決めている: `CFG_DEFAULT_FRONTEND_JOBS=2` を設定するのは nightly と dev のビルドだけ
  で、stable は逐次のまま。
- **バイナリは 1 つで、モードは実行時に決まる。** `cfg(parallel_compiler)` と `Lrc` はなくなった。
  `set_dyn_thread_safe_mode` はロックが 1 つもできる前に呼ばれる。1 スレッドのときはプールがなく:
  - `Lock` は再入で panic する `Cell<bool>`
  - `Sharded` のシャードは 1 つ
  - 自分自身に出会ったクエリはその場で循環になる

  N スレッドのときは、`Lock` は parking_lot の mutex、`Sharded` はキャッシュラインに揃えた 32 個のシャードで、FxHash の
  ビットで選ぶ。
- **並列に動くもの。** どれも本体の持ち主かモジュールを `par_for_each_in` で回す:
  - well-formedness の検査
  - typeck と定数評価
  - `mir_borrowck` (MIR はその中で必要に応じて作られる)
  - リント、可視性と未使用コードの検査
  - モノモーフィックなアイテムの収集 (後で並べ替える)
  - 最初の一群のコード生成単位

  構文解析、マクロ展開、名前解決、AST の lowering はまだ逐次。AST を並列に lowering する PR #163495 は、実行ごとに
  クレートのハッシュが変わるため merge queue で失敗した。
- **スレッドの下のクエリ。** 他のスレッドが計算中のクエリは latch (待つ側ごとの condvar) で待つ。スレッドをまたぐ循環が
  見つかるのは、プール全体が待ち状態になったときだけ。そのときデッドロックハンドラが動いているジョブを全部集め、待ちの
  グラフを探索して、1 回に 1 つの循環を切る。panic したクエリはキーを poison し、それを待つ側は fatal error を出す。
  キャッシュはシャードに分けたハッシュ表か、ロックのない `VecCache`。intern の表はシャードに分けた集合で、値はスレッドごとの
  アリーナ (`WorkerLocal<Arena>`) に置く。
- **決定性。**
  - 診断の順番はスケジュールで変わる (既知の問題)。並列の UI テストの CI ジョブは、出力の行を並べ替えてから比べる。
  - 出力の再現性は、並列に割り振ったものを振り直すことで保つ。`commit_end_of_determinism` は DefIndex の順番が揺れ始める
    点を示し、metadata はそれ以降の DefId を DefPathHash で振り直し、展開の id は安定したハッシュで振り直す。それでも
    ブログは、再現しないバイナリを既知のバグに挙げている。
- **メモリ。** 2023 年の記事は「最大 35%」増えるとしていた。2026 年の記事には数字がなく、メモリ不足への注意だけがある。
  8 スレッドを超えるとあまり伸びない。

zustc への教訓: rustc の仕組みの大部分は、スレッドが同時に辿る需要駆動のクエリのグラフのためにある。latch、デッドロック
ハンドラ、poison、出力を決定的に保つための振り直しがそれに当たる。zustc の検査とビルドはそういう形をしていない
(4.1 節)。

## 2. zustc の現状: fork した子と、順番どおりのマージ

zustc はすでに仕事の 3 か所を並列に動かしている。3 つとも `fork()` を使う:

| 部分 | 場所 | 単位 | 条件 |
|---|---|---|---|
| アイテムの要約 | `Session2::analyze` (driver2.rs) | アイテム | cold: 子 1 つあたり 32 個以上のミス |
| `check` | `check_many` (driver2.rs) | wave の関数 | 子 1 つあたり 32 個以上 (`ZUSTC_CHECK_FORK_MIN`) |
| 機械語 | `compile_many` (driver2/build.rs) | wave の関数 | 子 1 つあたり 16 個以上 |

ワークスペースのビルドも、クレートごとに子を fork する。

それぞれの子は、親の copy-on-write のスナップショットの上で `jobs` 個おきのアイテムを受け持ち、結果を pipe に書く。
関数は名前で書く (`encode_blob`) ので、子が振ったインスタンスの番号は外に出ない。親は結果を wave の順に読み戻す。関数を
読み戻すと、その関数が要求したインスタンスが要求し直されるので、次の wave と診断は 1 プロセスのときと同じになる。
tests/check_parallel.rs がこれを確かめている。panic した子や、送れないもの (`sendable`) があった子のアイテムは親がやる。

この機械 (4 コア、共有なので時間はばらつく) で、gen5000 の `zustc check --no-cache` は `-j 1` で 594 ms、`-j 4` の fork で
261 ms だった。2.3 倍で、rustc がスレッドで得ているものの大部分を、zustc はすでにプロセスで得ている。

fork の方式の限界:

- **スレッドのあるプロセスでは並列にならない。** `single_threaded()` は、スレッドが 2 つ以上あると fork しない。他の
  スレッドが持っているロックが子では持たれたままになるからである。zust-analyzer はスレッドを作るので、その診断の
  `check` はいつも逐次になる。
- **静的な割り当て** (`i % jobs == k`)。遅いアイテムがあると、その割り当て分の全体が遅れる。
- **並列にする区間ごとの費用**: fork と pipe と、送るものすべての encode と decode。閾値が子 1 つあたり 16〜32 個なのは
  このため。
- **戻せるのは encode できるものだけ。** それ以外は親がやり直す。
- **Unix でしか動かない。**

逐次の部分は大きい。gen5000 の `-j 4` では、prep (17 ms)、split (14 ms)、prelude (14 ms)、program (4 ms)、refs (3 ms) で、
約 260 ms のうち約 52 ms になる。

## 3. プロトタイプ: 同じ並列の部分をスレッドで

### 3.1 変えたもの

- **`zust-base::par`。** `map_with(jobs, n, chunk, init, f)` は `0..n` について `f(state, i)` を scoped thread で動かし、
  呼んだスレッドもその 1 つになる。
  - 各スレッドは自分の状態を `init` で作る
  - 番号は atomic なカウンタから `chunk` 個ずつ取る: 静的な割り当てではなく動的
  - 結果は番号の順に返る
  - `f` が panic した番号は `None` を返し、呼んだ側がやり直す (落ちた子と同じ)
  - `jobs` が 1 なら、呼んだスレッドでのただのループ
  - スタックは 8 MiB

  モードは `ZUSTC_PAR=fork|threads|off` (既定は `fork`) で決まる。ドライバをプロセスの中で動かすホストは
  セッションごとに `Options2::par` でも決められる。
- **アイテムの要約をスレッドで。** 要約は encode せず、値のまま戻る。
- **`check_many` をスレッドで。**
  - 子が関数ごとにしていた仕事を `send_checked` に移し、fork した子とスレッドで共有する。
  - 各ワーカーは wave の始めに 1 度 `Insts` (インスタンスの表) を複製する。これは fork した子が持つものと同じ。
  - 結果は名前で encode され、子のものと同じコードで、wave の順に読み戻される。
  - このため `Insts` と `Inst` は `Clone` を derive する。
- **`WorkerTls`。** ドライバがプログラムのために設定するスレッドローカルは `ast_closure::WILD_FAKE_READS`
  (クロージャの中の `let _ = place` についての edition の規則) だけである。これを呼んだスレッドで取り、各ワーカーで
  設定する。rustc の `tlv` に当たる。他のスレッドローカルは 1 つの計算のもの (深さ、メモ) で、新しいスレッドでは空から
  始まる。
- **AST のキャッシュ** (`Analysis::asts`) には問題が 2 つあった。
  - `compile_id_req` は関数を lowering する間ずっとロックを持っていて、ワーカーを 1 つずつしか動かさないところだった。
    木を `Arc` にし、lowering の前にロックを放すようにした。
  - 全関数の木を `Analysis` を drop するまで持っていた。その drop に、gen5000 の `zustc check -j 1` で **83 ms** かかって
    いた。スレッドでは 110 ms (他のスレッドで確保したメモリの解放)、fork では 2 ms だった (子の木は子と一緒に消える)。
    今はインスタンスの木だけを残す: ジェネリックな関数の本体はインスタンスごとに lowering されるが、普通の関数の本体は
    1 度だけである。drop はどのモードでも 1〜2 ms になった。これは逐次の検査も速くする。
- **テスト。** tests/check_threads.rs は `ZUSTC_PAR=threads` を `-j 4` と `-j 3` で、すべての wave と要約の pass を分けて
  (`ZUSTC_CHECK_FORK_MIN=1`, `ZUSTC_SUMMARY_PAR_MIN=1`) 動かし、`-j 1` と比べる。2 つ目のテストは、自分のスレッドを持つ
  ホストがワーカーを作り、fork せず、`-j 1` と同じ答えを得ることを確かめる。2 つのテストファイルが検査するプログラムは
  tests/check_parallel_program.rs に移した。

### 3.2 計測

生成したプログラム (`bench/gen.py`) の `zustc check --no-cache` を 4 コアで。時間は 7 回の最速と中央値。メモリは、
プロセスと fork した子の Pss の合計の最大で、1 ミリ秒ごとに測った。Pss を使うのは、1 つのプロセスの RSS では子の
メモリが見えないからである。どの行でも、診断は `-j 1` と同じだった。

| プログラム | モード | -j | 最速 | 中央値 | Pss の最大 |
|---|---|---:|---:|---:|---:|
| gen5000 | 逐次 | 1 | 593.8 ms | 665.6 ms | 35.7 MiB |
| gen5000 | fork | 2 | 356.3 ms | 443.2 ms | 36.1 MiB |
| gen5000 | threads | 2 | 338.8 ms | 361.3 ms | 44.5 MiB |
| gen5000 | fork | 4 | 260.6 ms | 294.7 ms | 36.7 MiB |
| gen5000 | threads | 4 | 253.6 ms | 284.7 ms | 44.3 MiB |
| gen20000 | 逐次 | 1 | 2176.1 ms | 2354.8 ms | 101.6 MiB |
| gen20000 | fork | 2 | 1513.1 ms | 1567.1 ms | 109.3 MiB |
| gen20000 | threads | 2 | 1358.9 ms | 1457.0 ms | 140.7 MiB |
| gen20000 | fork | 4 | 959.1 ms | 1003.8 ms | 116.5 MiB |
| gen20000 | threads | 4 | 933.8 ms | 1103.4 ms | 137.7 MiB |

段ごとに見ると (`ZUSTC_PROF=1`、gen5000、`-j 4`、2 回)、2 つのモードの差は実行ごとのばらつきの中にある: 要約は fork で
44〜62 ms、スレッドで 47〜63 ms、check は 171〜183 ms と 167〜177 ms だった。

診断は 513 個のプログラム (tests/compile_errors、tests/probe、examples、tests/acg、tests/security) でも比べた。それぞれを
`-j 1` で、次にスレッドの `-j 4` で 2 回、次に fork の `-j 4` で、すべての wave と要約の pass を分けて検査した。違いは
なかった。
`cargo test --release --workspace` は、crates/analyzer/tests/lsp.rs の 2 つのテスト (hover と型推論) を除いて通る。
この 2 つはこの環境では HEAD でも同じように失敗する。

数字からわかること:

1. **4 スレッドでは、スレッドは fork と同じ速さで動く。** どちらが速いかは数 % の範囲で入れ替わり、ロックの競合はまだ
   見えない: 4 つの intern の表のグローバルな mutex、`AdtTable` の mutex、AST のキャッシュ。つまり、スレッドにする
   だけではコマンドラインは速くならない。
2. **スレッドではメモリが 18〜29% 多い**: gen5000 で +8 MiB、gen20000 で +21〜+31 MiB。malloc のアリーナの数のせいでは
   ない。`MALLOC_ARENA_MAX=2` では Pss の最大は同じ (134 MiB) で、検査はおよそ 1.0 s ではなく 1.8〜3.7 s かかった。
   スレッドが malloc で順番待ちになるためである。考えられる原因 (確かめていない):
   - ワーカーごとの `Insts` の複製
   - ワーカーごとのアリーナが、解放したものの最高水位を持ち続けること。fork した子は終わるときにそれを返す。
3. **スレッドで得られるものは別のところにある:**
   - スレッドのあるプロセスでの並列化。何よりも LSP
   - 並列の区間ごとの費用が小さく、閾値を下げられること
   - 動的なスケジュール
   - ワーカーの間で encode が要らないこと (まだ使っていない)
   - `fork` のないプラットフォーム

## 4. 設計

### 4.1 wave を残し、クエリシステムは作らない

rustc のスレッドは、需要駆動のクエリのグラフを辿る。他のスレッドが計算中の結果を必要とするスレッドは、それを待たなければ
ならない。latch、スレッドをまたぐ循環を見つけるデッドロックハンドラ、poison されたキー、スケジュールで変わる診断、
並列に割り振った id の振り直しは、すべてここから来ている。

zustc の検査とビルドは、すでに **wave** (bulk-synchronous) で動いている:

- wave は互いに独立な関数の集まり
- バリアで終わる
- 結果を決まった順にマージし、そのマージが次の wave を作る

設計はこの形をスレッドでも保つ:

- **作りからして決定的。** マージは wave の順で、診断は並べ替えるので、`-j` やスケジュールで出力は変わらない。rustc の
  並列の UI テストは行を並べ替えてから比べる必要があるが、zustc の tests/check_parallel.rs はそのまま比べる。
- **仕事が互いを待たない。** だから latch もデッドロックハンドラも、スレッドをまたぐ循環もない。
- **仕事の結果は、wave の始めのスナップショット**と、そのワーカーが同じ wave で先にしたことだけで決まる (fork した子と
  同じ)。

費用は、バリアでの待ち時間と逐次のマージである。前者は chunk ごとの動的なスケジュールで減らす。後者は測るべきである
(マージの `ZUSTC_PROF` の行)。

### 4.2 状態の 4 つの種類

| 種類 | 例 | 規則 |
|---|---|---|
| 並列の部分の間は読むだけ | `Program` の表、`items`、`src`、`refs` | `&` で共有し、ロックなし (rustc の `FreezeLock`: 作ってから凍らせる) |
| 追加だけ、値がキー | intern の表 (`Ty`、`FnTy`、文字列、関連型)、`AdtTable` のインスタンス、`normalized` / `inst_keys`、AST のキャッシュ | ロックの後ろで共有する。ここで振った id は、出力にもマージの順番にも届いてはならない |
| 仕事の作業状態 | `Insts`: `pending`、`fx_log`、`closure_rg`、`kind_free` | ワーカーごとの複製。名前で、順番にマージする |
| ドライバが設定するスレッドローカル | `WILD_FAKE_READS` | 呼んだスレッドで取り、各ワーカーで設定する (`WorkerTls`) |

`Insts` はワーカーごとでなければならない。`send_checked` は関数が作ったものを位置で見つける (`pending[p0..]`、
`fx_log[l0..]`) が、これは表に書くスレッドが 1 つのときにしか成り立たない。

id の規則は、rustc が #163495 と DefId の振り直しから得た教訓である。zustc の名前による encode は、すでにその振り直しを
している: ワーカーで作った `AdtTable` の struct のインスタンスは実行ごとに違う番号になるが、キャッシュと診断が見るのは
名前だけである。ビルドをスレッドに移すときは、`.o` が `-j` と実行によらず同じになることを確かめなければならない
(self-host の不動点がすでに確かめているように)。

### 4.3 バイナリは 1 つで、モードは実行時に決める

rustc と同じく、1 つのバイナリが 3 つのモードを持ち、`jobs` が 1 ならただのループで動く。zustc はすでにどこでも `std` の
mutex を使っている: これを書きながらのコンパイル時の確認で、`Analysis`、`Program`、`Session2` が `Sync`、`Insts` が
`Send` であることを確かめた。競合しない mutex は安いので、rustc の `DynSync` / `Lock` のモードの仕組みは要らない。

既定はホストに合わせるのがよい:

- **スレッドのあるプロセスでは:** スレッド。zust-analyzer もこれに当たり、`Options2::par` を設定する。jobs は 2 にする
  (rustc がメモリとエディタ自身のスレッドのために選んだもの)。
- **1 スレッドのプロセスでは:** メモリでスレッドが追いつくまでは fork。

### 4.4 仕事の配り方

- 動的な chunk: 要約は 4 個、check は 2 個。
- 閾値は fork から引き継いだもの (ワーカー 1 つあたり 32 個)。スレッドでは、並列の区間の費用はスレッドをいくつか作る
  ことだけである。閾値は測り直し、得になるなら下げる。そうすれば、中くらいの編集の後の検査も並列にできる。
- wave の間はワーカーを待たせておく常駐のプールなら、スレッドを作る費用もなくなる。しかしプールのあるプロセスには
  スレッドがあるので、その後は fork できない。各プロセスは、全部スレッドか全部 fork かのどちらかにすることになる。
  それを決めるまでは、区間ごとの scoped thread なら両方を残せる。

### 4.5 失敗

- **panic。** panic したアイテムは捕まえて、呼んだスレッドでやり直す。fork した子と違い、共有の mutex を持ったまま panic
  したスレッドは、その mutex をプロセス全体で poison する (`AdtTable` とキャッシュ)。方法は次のどちらか:
  - 共有のキャッシュは panic をまたいで保つ不変条件を持たないので、`lock().unwrap_or_else(|e| e.into_inner())`
    で取る
  - panic の後は、その wave の残りを逐次で終える

  rustc の `ParallelGuard` は、区間の仕事を全部終えてから panic を投げ直す。
- **スタック。** ワーカーは 8 MiB。rustc は 17 MiB で、windows-gnu では並列が既定になった後にスタックあふれが増えた
  (#166530)。

### 4.6 メモリ

- KPI の「cold build の peak RSS」は 1 つのプロセスを測る。fork した子のメモリはそこに入らないが、ワーカースレッドの
  メモリは入る。既定を変える前に、KPI を 3.2 節のようにプロセスの木全体の Pss で測るようにする。そうしないと、変更が
  実際より悪く見える。
- 18〜29% を取り戻すには:
  - 重ねる形の `Insts`: 全ワーカーが読むだけで共有するスナップショットと、ワーカーごとの小さな差分。ワーカーごとの
    完全な複製の代わりにする
  - 並列の区間の後の `malloc_trim`
  - 関数の一時的なデータのための、ワーカーごとのアリーナ (rustc の `WorkerLocal<Arena>` のように)

### 4.7 intern の表とキャッシュ

intern の表は 4 つのグローバルな `Mutex<FxSet>` である。4 スレッドでは競合は見えなかった。rustc の答えは、ハッシュの
ビットで選ぶ 32 個のシャード (`Sharded`、`SHARD_BITS = 5`、8 コアで調整したもの) と、スレッドごとのアリーナである。
計画では、まず測る: 8 コア以上でロックの待ちを数える (CI のランナーは 4 コア)。intern の表をシャードに分ける (16〜32 個、
FxHash のビットで選ぶ) のは、そこに現れたときだけにする。

### 4.8 逐次のまま残るもの (Amdahl)

gen5000 の `-j 4` では、260 ms のうち約 52 ms が逐次である: prep、split、prelude、program、refs。8 スレッドなら並列の部分は
約 100 ms になるので、逐次の部分は約 3 分の 1 になる。展開、名前解決、lowering がまだ逐次の rustc と同じく、ここが一番
難しい:

- `macro_rules!` は順に展開する
- `mod x;` のファイルは見つけた順に読む

候補は、ファイルごとの字句解析と分割の並列化と、prelude の選択である。その前にすることがある: self-host のコンパイラの
ソース (1 ファイルで 95k 行) では、prep だけで 1.4 s かかった。並列化の前にこれをプロファイルするべきである。スレッドとは
関係のない hot spot かもしれない。

### 4.9 ワークスペースと jobserver

ワークスペースのビルドはクレートごとに子を fork し、各クレートはさらに関数を分けるので、`-j` が 2 段でかかる。
`zurgo test` もテストを並列に動かす。スレッドなら、プロセス全体で 1 つのトークンの予算を持てば使いすぎを防げる。rustc の
jobserver の `Proxy` には、真似する価値のある規則が 2 つある: プロセスの最後のトークンは決して返さないこと、空いた
トークンを待っているスレッドに直接渡すこと。

### 4.10 self-host

zustc 自身のスレッドは green thread (OS のスレッドは 1 つ) で、`thread::scope` がない。そのため `par.rs` は self-host の
対象の外に置く: self-host のビルドでは、逐次の `map_with` をその代わりに置く。

別件として、`tests/selfhost/build_compiler.py` は `driver2/dead.rs` (d9e104a で追加) を中に入れないので、HEAD では
self-host のコンパイラのビルドが "file not found for module `dead`" で失敗する。今回の変更とは関係がない。

## 5. 作業の順番

1. スレッドのあるプロセスでは既定をスレッドにし、zust-analyzer では 2 jobs にする。zustc 自身のソースでその診断を測る。
2. `compile_many` をスレッドで。`.o` が `-j` と実行によらずバイト単位で同じことを確かめる。
3. メモリ: 重ねる形の `Insts` と `malloc_trim`。プロセスの木の Pss で測り直す。
4. スレッドの閾値。関数を 1 つ編集した後の検査とビルドを測る。
5. 8 コア以上で測る。intern の表に競合が出たらシャードに分ける。
6. prep をプロファイルし (self-host のソースで 1.4 s)、その後でファイルごとの字句解析と分割を並列にする。
7. その後で、コマンドラインの既定 (fork かスレッドか) を決める。

予定にないもの: latch を持つクエリシステム。

## 測っていないもの

- 4 スレッドより多い場合: この機械は 4 コア。
- スレッドでのビルド (`compile_many` は変えていない)。
- スレッドでの zust-analyzer の応答時間。
- ジェネリックの多いプログラム。`Insts` の複製が大きくなり、重ねる形が効くところ。
