# リージョン (ライフタイム) 検査、その 23: 外からの領域に対するプレースホルダー、プレースホルダーの境界の型引数、発散する初期化式、パラメータが 2 回現れる型エイリアス (issue #1)

日付: 2026-11-24

その 22 ([2026-11-24-08](2026-11-24-08-region-check-22.md)) は #124 でマージした。この段階で加えるもの:

- クロージャのシグネチャのプレースホルダーを、その外からの領域が免除するのは、その領域がそれより長生きすると分かって
  いるときだけにする;
- 何も呼ばないジェネリックな関数での、トレイトの型引数がライフタイムを指すプレースホルダーの境界のメソッド;
- 初期化式が発散する `let` の注釈の well-formedness;
- 穴を持ち、パラメータがエイリアスの中に 2 回現れる型エイリアスの注釈。

## 1. 加えたもの

- **プレースホルダーを免除するのは、外からの領域がそれより長生きすると分かっているところだけである。**
  `F: for<'b> FnOnce(&'b u32, &'a u32) -> &'b u32` と `x: &'x u32` の `take(x, |_, _| x)` を受理していた (rustc では
  「lifetime may not live long enough」)。外からの領域 (呼び先の `'a`) を持つクロージャのシグネチャは、どの
  プレースホルダーも、関数の領域が長生きしなければならないことから免除していた: 境界の含意するものがそれらを結びつける
  かもしれないからである (closures/explicit-closure-lifetime-issue-87290.rs の `impl FnOnce(&mut &mut &'a i32)`)。今は、
  シグネチャの implied bounds によって外からの領域が長生きすると分かっているプレースホルダーだけを免除する: `&'a u32` の
  隣の `&'b u32` は `'b` について何も含意しないので、`'x` はどの `'b` よりも長生きしなければならない。これは #111 の
  レビューから来た。
- **トレイトの型引数がライフタイムを指す、プレースホルダーの境界のメソッド。** 2 つのプログラムを受理していた:
  - `F: FnLike<&'a isize, &'a isize>` とローカルの x で `f.call(&x)` (rustc では E0597): 引数は `&'a isize` なので、x は
    `'a` より長生きしなければならない;
  - `F: for<'a> FnLike<&'a isize, &'a isize>` で `let y = f.call(&x); x = 5; drop(y);` (E0506、
    higher-ranked/trait-bounds/hrtb-identity-fn-borrows.rs): 結果は引数の領域のものである。

  3 つの変更でこれを扱う:
  - 何も呼ばないジェネリックな関数はプレースホルダーで検査するが、宣言がライフタイムを指さない境界のトレイトの
    メソッドを呼ぶものは検査しなかった。今は、境界の引数がライフタイムを指すところでは検査する。
  - プレースホルダーのメソッドの、引数が与えないトレイトのパラメータは、今は境界の引数である:
    `fn call(&self, arg: A) -> R` の `R` は型検査に失敗していた (「cannot infer type parameter」)。
  - リージョン検査は、トレイトの型引数の木を、書かれた境界から取る。関数が指さないライフタイムは境界自身のもの
    (要約が持たない `for<'a>`) で、呼び出しに 1 つの新しい領域とし、引数たちがそれを共有する。
- **初期化式が発散しても、`let` の注釈は well-formed である。** `let _: &'a S<'b> = loop {};` を受理していた (rustc では
  「lifetime may not live long enough」: `'b` が `'a` より長生きしなければならない)。発散する初期化式は、リージョン検査の
  前に `let` を抜けていた。今は、名前の束縛でも `_` でも、注釈の木とその well-formedness を、初期化式のない `let` と同じに
  取る (regions/regions-outlives-projection-container-wc.rs、-hrtb.rs、
  regions-assoc-type-in-supertrait-outlives-container.rs)。
- **穴を持ち、パラメータがエイリアスの中に 2 回現れる型エイリアスの注釈。** `type DoubleCell<A> = Cell<(A, A)>` で
  `let x: DoubleCell<_> = make_cell(&b);` を受理していた (rustc では E0597、nll/relate_tys/var-appears-twice.rs)。穴の
  領域は場所ごとに新しかった。今は、エイリアスの本体をパラメータごとに 1 つの木 (引数のもの、穴なら新しいもの) で
  インスタンス化し、パラメータの出現たちがそれを共有する。`Cell` の下ではそれらは不変なので、`&'b u32` は隣の
  `&'static u32` でなければならない。`DoublePair<_>` (タプル、共変) は rustc と同じく受理する。エイリアス自身の領域は
  新しい。要約がその定義のライフタイムを持たないからである。

## 5. まだ扱わないもの

- **そういう境界を持つ、呼ばれるジェネリックな関数** (`F: FnLike<&'a isize, &'a isize>` の `call_repeatedly(Id)`):
  呼ばれるインスタンスを impl のメソッドで検査し、それは境界の領域について何も言わない。プレースホルダーで検査するのは、
  何も呼ばないジェネリックな関数だけである。
- **main にもここにもある誤った E0308**: `trait Get<'a> { fn get(&self, arg: &'a isize) -> &'a isize; }` と
  `F: for<'a> Get<'a>` で、`let x = 3; f.get(&x)` (rustc は受理する)。接尾辞のない整数リテラルのローカルを渡す
  プレースホルダーのメソッドの引数が、メソッドが `&isize` を取るところで `&i32` になる。
- **結果が穴の関数ポインタの注釈** (`let f: fn(&u32, _) -> _ = first::<u8>;`、rustc では E0308「one type is more
  general than the other」): 穴は、ポインタの束縛する領域を指せない。
- **リージョン検査が始まっていない関数での型エイリアスの注釈**: ライフタイムを指さず `'static` も書かない関数の
  `let x: DoubleCell<_> = make_cell(&b);` は検査しない。

- **呼び出しでの、射影を正規化した型** (`fn test<'a>(x: &'a u8, _wf: <&'a u8 as Tr>::Ty)` の `test(&x, &&3)`、
  implied-bounds/assoc-ty-wf-used-to-get-assoc-ty.rs の 24 行目): 呼び先の要約は、型が射影のパラメータのコードを持たない
  ので、呼び出しはそれを辿らない。関数の中と `let` の注釈では、今は辿る。
- **関数ポインタ型の型エイリアスへのキャスト** (`type F = fn(&u32);` の `c as F`): 要約はエイリアスの定義のライフタイムを
  持たない (第 4 節)。
- **結果が抜け出す領域のあいだ借用される、クロージャの `ref` パラメータ** (`.filter_map(|ref line|
  self.make_entry(line))`、borrowck/cannot-return-ref-to-fn-param-in-filter-map.rs の 6 行目)。
- **ライフタイムを固定する関数ポインタ型の型エイリアスを通して渡す関数アイテム**: `type G = for<'cx> fn(&'cx S) ->
  &'static S;` の `want_G(baz)` (regions/regions-fn-subtyping-return-static-fail.rs)。要約はエイリアスの定義の
  ライフタイムを持たず、関数の要約はそのモジュールのエイリアスを見ない。
- **関数ポインタ型の別々の束縛ライフタイム** (`for<'a, 'b> fn(&'a u32, &'b u32) -> &'a u32`) は、関数アイテムを渡す
  ところで 1 つのプレースホルダーになる: 領域のコードは束縛を持たない (その 19 の第 4 節)。
- **関数で作り、別のクロージャの本体で呼ぶクロージャ** (adt-tuple-struct-calls.rs の
  `annot_reference_named_lifetime_across_closure`)。内側の本体は、外側のクロージャのシグネチャなしで単独に検査する。
- **struct のフィールドを通して、または別のクロージャの本体で呼ぶクロージャの、呼び出しが借用するもの**
  (closures/issue-113087.rs)。持つのは、ローカルの名前で呼ぶクロージャだけである。
- **使われない定数の初期化式** (main の中の `const z: &'static isize = { let p = 3; &p };`、static/issue-18118.rs) と、
  定数の初期化式のブロックの中の関数アイテム (borrowck/borrowck-fn-in-const-c.rs)。定数は使うところで展開して検査する。
- **型がトレイトのライフタイムを指すトレイトの定数** (`<T as Foo<'a>>::C`、`T: Foo<'a>` の `T::C`、
  nll/user-annotations/constant-in-expr-trait-item-2.rs、-3.rs)。何も呼ばないジェネリックな関数は、定数を使うところに
  届かない。
- **ガードの一時値を通して読む `&mut` の暗黙の再借用** (後で使う `let val: &_ = x.borrow().0;`、
  borrowck/issue-36082.rs)。
- **スライスでも `str` でもない型の `Cow<'_, T>`**、関数の中の `use std::option::Option::Some as S;`
  (lifetimes/temporary-lifetime-extension-tuple-ctor.rs)。
- **`let` の初期化式以外で値としてムーブされる `&mut`**: ジェネリックな f の `f(a[0])`、`vec![a[0]]` (E0508)。
- その 17 から:
  - 1 か所に書いたプログラムの 2 つの deref (`(&mut **w).bump()`);
  - ある型への impl があいまいなトレイト (borrowck/mut-borrow-in-loop-2.rs)。
- その 16 から:
  - ジェネリックな関数の `dyn Tr<T>`;
  - `&*vec![1].iter().next().unwrap()`;
  - opaque 型のメンバー制約 (E0700);
  - タプルの推論の中の `&mut`;
  - フィールドごとの領域;
  - `static` クロージャの借用検査。
