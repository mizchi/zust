# リージョン (ライフタイム) 検査、その 31: クロージャの中のエラーをクロージャで、自身の局所変数を借用する const のブロック、一時値の検査される値からのムーブ、ムーブした値の使用のうち rustc が出すもの、drop の前に読むブロックの値 (issue #1)

日付: 2026-11-25

その 30 ([2026-11-25-02](2026-11-25-02-region-check-30.md)) は #156 でマージされた。この段階で加えるもの:

- 自身の位置を持たない、クロージャの本体の中のエラーを、そのクロージャで出す;
- 自身の局所変数の借用で終わる、const や static の初期化子のブロックの E0597;
- 場所でない検査される値からの、`&` パターンを通したムーブ (`match (l1, l2) { (_, &[hd, ..]) => .. }`);
- 1 つのムーブがムーブしたものの使用のうち、rustc が出すもの;
- 書かれた `Vec<_>` への `collect` が与えるものを、その `let` で知る;
- ブロックが drop するものから読み出した `Copy` の集約値であるブロックの値を、drop の前に読む (zustc が生成する
  コードの修正)。

## 1. 加えたもの

- **自身の位置を持たない、クロージャの本体の中のエラー。** クロージャのパラメータのパターンによる、参照からのムーブを
  考える: `HashMap<String, i32>` に対する `.filter(|&(&_k, &_v)| true)`。zustc はそれを、クロージャを含む fn の最初の
  行で、「in `main::{closure#0}::call`」として出していた。rustc はクロージャで出す。
  - そういうエラーは、今はクロージャの行にある。
  - これで 4 つのテストが通る。どれも rustc がクロージャの中で出すエラーを持つ:
    - liveness/liveness-issue-2163.rs;
    - moves/do-not-suggest-removing-wrong-ref-pattern-issue-132806.rs;
    - pattern/type-alias-as-variant-pattern.rs;
    - pattern/usefulness/refutable-pattern-in-fn-arg.rs。
- **自身の局所変数を借用する、const や static のブロック。** `const Z: &'static isize = { let p = 3; &p };` を考える。
  値は `'static` であり、`p` はブロックの終わりでなくなる。rustc は `&p` で E0597 を出す。zustc は受理していた。
  - 今は E0597 である。フィールドや添字を通したもの (`&p.0`、`&p[0]`) でもそうである。fn の本体の中に書かれた const や
    static でも、それが書かれた行でそうである。
  - リテラルの借用 (`{ let _p = 3; &5 }`) は static に昇格され、rustc と同じく受理する。
  - consts/const-eval/generic-slice.rs、consts/issue-78655.rs、static/issue-18118.rs が通る。
- **一時値の検査される値からの、`&` パターンを通したムーブ。**
  - `l1, l2: &[String]` での `match (l1, l2) { (&[], &[hd, ..]) => .. }` を考える。検査される値は一時値のタプルで、
    そのパターンには照らし合わせる場所がなかった。zustc は、参照の向こうのスライスからの `hd` のムーブを受理していた。
    rustc は E0508 を出す。
  - そういう検査される値は、今は自身の隠れた局所変数を持つ。それは、あるパターンが `&` の下で値で束縛し、どれも `ref`
    で束縛しないところで作られる。
  - 参照を通したムーブは、今は局所変数のそれと同じく、検査される値のところでのエラーである。それは rustc の行にある
    (E0507 / E0508)。
  - `Copy` の束縛 (`n: u32` での `(_, &Some(n))`) と `ref` の束縛は、rustc と同じく受理する。
  - 3 つのテストが通る:
    - match/slice-move-out-error-12567.rs;
    - pattern/by-move-pattern-binding.rs (`match &s.x { &E::Bar(identifier) => .. }`);
    - traits/trait-object-destructure.rs。その行は rustc のものだが、そのメッセージはムーブのエラーで、rustc の E0033
      (トレイトオブジェクトは deref できない) ではない。
- **ムーブした値の使用のうち、rustc が出すもの。**
  - `continue` が抜ける内側のループでムーブされた `foo` を考える。`foo` は、そのループの次の反復 (`foo == *bar`) と、
    ループの後 (`qux.push(foo)`) で再び使われる。
  - rustc はムーブごとに 1 つの使用を出す: その MIR の逆後順で最初のものである。そこではループから出る道が本体の前に
    来る。それはループの後の使用である。zustc は行で最初のものを出していた。
  - 1 つのムーブがムーブしたものの使用のいくつかがエラーであるところでは、今は残すものは、ムーブがある自然ループの
    うち最も少ないものにあるもので、次にブロックの逆後順で最初のものである。zustc の範囲に対するループは、その終わり
    で判定するので、ループが先に決める。
  - moves/nested-loop-moved-value-wrong-continue.rs が通る。範囲に対するループ、`while`、スライスに対するループ、
    入れ子のループは、rustc の行にある。
- **`Vec<_>` への `collect` が与えるもの。** `let parts: Vec<_> = s.split('|').collect();` の後に、`&'a str` として
  返す `&parts[0]` を考える。
  - zustc の推論は、要素の型をその使用から取っていた: `&str` としての `&parts[0]` は、要素を `str` にした。fn の
    終わりでだけ、それをイテレーターの `&str` と単一化し、それは失敗していた。
  - そのため、`&&str` は `parts` から借用した `&str` とされた: 誤った E0515 である。
  - rustc は `let` で `FromIterator` の impl を選ぶ。今は、そこで要素はイテレーターの要素である。
  - `&T` と単一化した `&&T` (deref の強制変換) も、もう 2 つの参照を 1 つの型にはしない。
  - borrowck/cannot-return-ref-to-fn-param-in-filter-map.rs の make_entry は、今は rustc と同じく受理する。
- **drop の前に読むブロックの値。** これは zustc が生成するコードの修正で、上のケースを rustc と照らし合わせる間に
  見つけた。
  - `fn f() -> (i64, i64) { let v = vec![(1, 2)]; v[0] }` を考える。ブロックの値は要素のアドレスで、`v` を drop した
    後に読まれていた。main ではでたらめな値を表示し、`Vec<&str>` の `v[0]` はクラッシュした。
  - Box の `*b` と `b.0`、`return v[0];`、そして `&str` として返す `&&str` の局所変数の deref の強制変換でも同じ
    だった。
  - そういう値 (新しい一時値でない `Copy` の集約値で、ブロックが何かを drop するところのもの) は、今は rustc が末尾を
    先に評価するのと同じく、drop の前にコピーして取り出す。期待される型への deref の強制変換も、その前にする。
  - スタックスロットのアドレスにある値 (局所変数のもの、match の結果のもの) はコピーしない。どの drop もスタックスロットを
    解放しないからである。どの値がそれであるかは IR が教える。
  - 新しい driver2 の probe である tests/probe/tail_copy_out.rs が、これらのケースをビルドして実行する。期待する出力は
    rustc 1.97 のものである。

## 4. レビュー

- **main が進んだ。** PR を開いている間に #127 がマージされ、その compile-fail の数は 4684 だった。main (b642ce0) を
  PR にマージした後の数は 4695 で、新しく通るのは同じ 11 のテストである。退行は 0、新たに拒否する run-pass のテストは
  なく、`cargo test` は通る。
- CodeRabbit は 6fd0ccd の PR をレビューし、4 つを指摘した。どれも zustc と rustc 1.97 で確かめ、4 つとも直した:
  - **括弧の中の `collect`。** `let parts: Vec<_> = (s.split('|').collect());` は、まだ誤った E0515 を出していた。
    `collect` の検査は、今は括弧の中を見る。
  - **深さの違う参照。** `&&u8` として渡す `&&&u8` は `&&u8` の型とされ、`***c` は「`u8` cannot be dereferenced」
    だった。rustc は受理する。
    - 2 つの参照の連なりが深さの違う分かった形で終わるところでは、参照どうしはつながず、最も内側の型どうしだけを
      単一化する。
    - これまでは、1 段の違いだけを見ていた。
  - **局所変数の参照を通した const の借用。** `let p = &DATA; &p.0` は局所変数ではなく `DATA` を借用するが、E0597
    だった。
    - 局所変数のフィールドや要素は、今はその局所変数が集約値を持つところでだけ、自身の置き場所とする: 参照でない
      書かれた型か、そこで作られた値である。
    - `let p = (3,); &p.0` は、rustc と同じく今も E0597 である。
  - **`&mut` からのムーブ。** メッセージは「shared reference」と言っていた: 検査は `Deref(true)` (Box の deref) を
    `&mut` のものと取っていた。`&mut` のものは `Deref(false)` である。今は「a mutable reference」と言う。
  - tests/regionck.rs が 4 つのケースを確かめる (`part31_review`)。

## 5. まだ扱わないもの

- **境界のメソッドを呼ぶジェネリックな本体でのムーブ。** `T: Foo` の `fn zero(self)` での 2 度の `x.zero()` は、`T`
  が `u32` でだけインスタンス化されるか、まったくされない間はエラーでない。ジェネリックな fn がプレースホルダーで検査
  されるのは、その本体が境界のトレイトのメソッドを呼ばないところだけである。それはその型検査を要するからである (traits
  の KPI の +4.9%)。そういう fn は、代わりにインスタンスごとに検査される (binop/binop-consume-args.rs、
  moves/issue-34721.rs)。
- **キャプチャした参照を通してメソッドを呼ぶクロージャに対する、誤った E0373。** `h: &'r H<'r>` の fn から返す
  `v.iter().filter_map(|_| h.mk()).collect()` を考える。zustc はクロージャが `h` を借用すると出す。rustc は受理する。
  - `h` のキャプチャは `*h` でなく `h` のものである。
  - 集めた値は、クロージャが保つものを保つとされる。
- **呼び出しを通して自身のパラメータを借用する、クロージャの結果。**
  `filter_map(|ref line| self.make_entry(line))` は rustc の E0515 である
  (borrowck/cannot-return-ref-to-fn-param-in-filter-map.rs)。zustc は受理する。
- **マクロの中の位置。** `macro_rules!` の展開の中のエラーは呼び出しにある。rustc はマクロの定義の中を指す
  (borrowck/span-semicolon-issue-139049.rs)。
- **`@` の束縛。** `a @ NC(b, c)` や `ref a @ b` のムーブと借用は検査しない (pattern/bindings-after-at/*)。
- その 30 以前から: [その 30](2026-11-25-02-region-check-30.md) の第 5 節を見よ。
