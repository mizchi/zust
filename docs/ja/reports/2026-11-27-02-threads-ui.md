# OS スレッドの上で rustc のスレッドのテストを通す

Date: 2026-11-27

[レポート 2026-11-27-01](2026-11-27-01-native-threads.md) の後も、スレッドについての rustc の UI テストのいくつかは
通らなかった。`tests/ui/threads-sendsync/`、`tests/ui/thread-local/`、`tests/ui/std/` のものである。このレポートでは、それらに要るものを足す。どれも特定の 1 つのテストのためのものではない。

## 変えたこと

### `thread::Builder`（recursive-thread-spawn）

std と同じく `Builder::new().name(..).stack_size(..).spawn(f)`。`spawn` は `io::Result<JoinHandle<T>>` を返し、
`pthread_create` の失敗はそこでは `Err` になる（`thread::spawn` はこれまでどおりそれで panic する）。スタックの大きさはページ単位に切り上げ、
少なくとも 64 KiB にする。glibc は `PTHREAD_STACK_MIN`（16 KiB）より小さいものを受け付けず、std はそれより小さいものをそこまで上げる。
zustc の下限はそれより高く、自分のフレームのための余裕である。名前はスレッドの共有部分（`__ThreadInner`）に置く。`Thread::name()` がそれを返し、
そのスレッドでの panic は std と同じく `thread '<name>' panicked at ..` を出す。`thread::spawn` は、名前なし、2 MiB の `__exr_spawn` である。

### クロージャは借りているものを通して Sync になる（send-is-not-static-par-for）

クロージャが参照で持つキャプチャは、その構造体の生ポインタのフィールド（`*mut T`）である。生ポインタは Send でも Sync でもないので、
rustc のクロージャは `&Mutex<_>` を持つのに、`|x| *m.lock().unwrap() += x` は `F: Sync` を満たさなかった。auto trait を判定する
3 か所（`Program::auto_trait`、トレイトソルバの `auto_rec`、acg の `auto_trait_fails`）は、そういうフィールドを、それが表す `&T` として扱うようにした。
つまり T が Sync なら Send でも Sync でもある。それは `Program::ref_capture` で、クロージャの定義から見つける（`move` でないクロージャの、ムーブされていないキャプチャ）。
クロージャが値として持つ生ポインタ（`move || unsafe { *p = 1 }`）はこれまでどおりどちらでもなく、借りた `Cell` や `Rc` も rustc と同じく
`Sync` と `Send` を満たさない。`thread::spawn` は変わらない。そこでの借用は先に E0373 になる。

### `mpsc`: `recv_timeout`、`into_iter`（mpsc_stress）

- `Receiver::recv_timeout(d)` は `recv` と同じく待つが、futex をタイムアウト付き（`FUTEX_WAIT` の相対 `timespec`）で待ち、
  `CLOCK_MONOTONIC` が期限を過ぎるまで待つ。過ぎたら `RecvTimeoutError::Timeout` を、送り手が残っていなければ `Disconnected` を返す。
  std と同じで、Display の文も std のものである。時計を読むのは `recv_timeout` だけなので、それを呼ばないプログラムは時計を要らない。
- `Receiver::into_iter()` は受け手をイテレータの中に持つ（`__RecvIntoIter`）。そのためループの間、送り手からは受け手が生きて見える。

### `thread::park_timeout`（std/park-timeout-wakeup-59020）

std と同じ。トークンがあればすぐに取る。なければタイムアウト付きで futex を 1 回待ち、その後で状態を empty に戻す（その間に与えられたトークンは取られる）。
std と同じく、早く戻ることがある。

### `sync::Barrier`

std と同じく、ロックの下のカウントと世代である。カウントを n にしたスレッドがリーダー（`BarrierWaitResult::is_leader`）になる。
リーダーは次の世代を始めて、ほかのスレッドを起こす。ほかのスレッドは、世代ごとに増える futex の語を待っている。
プログラム自身の `struct Barrier`（mpsc_stress にある）は、ほかの std の名前と同じくこれを隠す。

### thread_local!（tls-init-on-init、tls-try-with）

- 初期化子が同じ thread_local! にもう一度届くと（その `with`）、内側が先に値を作る。std は外側の初期化子の値を残し、内側の値を後で drop する。
  `with` も今はそうする。スロットを置き換え、それから古い値を drop する（`lexer::expand_thread_local`）。
- 本体が `panic!(..)`（または `unreachable!`、`todo!`、`unimplemented!`）だけで、ほかに型を決めるもののないクロージャは `!` を返す。
  これまでは戻り値の型が決まらないまま残り、呼び出しが失敗していた（`FOO.try_with(|_| panic!(..))`）。
  これは rustc のフォールバックで、rustc 1.100 からはどのエディションでも `!` である。呼ばれる側の型パラメータの境界は、呼び出しが解決されるところで
  `!` に対して調べる。`R: Bar` での `foo(|| panic!())` は rustc と同じく E0277 になる
  （never_type/fallback_change/fallback-closure-ret.rs。`()` にしたときは受け付けてしまっていた）。

## 確かめたこと

- `tests/threads/builder.rs`（新規。両方のバックエンドで、rustc の出力と比べる）：名前付きのスレッドと名前なしのスレッド、小さいスタック、
  panic のメッセージの中の名前（stderr）、`park_timeout`（タイムアウトするもの、トークンがあるもの、別のスレッドから unpark されるもの）、
  期限内、タイムアウト、切断の `recv_timeout`、4 つの送り手にわたる `into_iter`、6 スレッドで 50 回の `Barrier`
  （早く通り抜けるスレッドはなく、回ごとにリーダーは 1 つ）、send-is-not-static-par-for の `par_for`。
- クロージャの auto trait を rustc と比べた。借りた `Cell` や `Rc` は Sync でなく、借りた `Cell` があるとクロージャは Send でなく、
  ムーブで入れた生ポインタは Send でなく、借りた `Mutex` は Send でも Sync でもある。
- rustc の UI テスト（rust_ui.py）：後退は 0、新たに通るのは 6 つ。threads-sendsync/mpsc_stress.rs、
  recursive-thread-spawn.rs、send-is-not-static-par-for.rs、tls-init-on-init.rs、tls-try-with.rs と
  std/park-timeout-wakeup-59020.rs。threads-sendsync では今 59 のうち 52 が通る（前は 47）。
- `cargo test --release --workspace`。

## 残っていること

まだ通らないスレッドのテストには、ほかのものが要る。

- std-sync-right-kind-impls: `sync::Weak` と、zustc にない `net::TcpStream` / `TcpListener` / `UdpSocket`。
- send_str_hashmap、send_str_treemap: 後の使い方から推論される、マップの値の整数リテラルの型。
- sync-send-in-std: `to_socket_addrs`（名前解決）。
- sync-send-iterators-in-libcore: それが使うマクロ。
- tls-in-global-alloc: `#[global_allocator]`。
- unwind-resource: 巻き戻し。
