# Multiple crates with many dependencies (`bench/deps_bench.py`)

Date: 2026-11-16

The leaves are 6 real crates from cratebench; above them are N generated intermediate crates (a DAG where each depends on 2 to 3 real crates and on up to 3
previous intermediate crates, using structs, traits, generic functions, closures and cfg_if!); an app sits at the top. We compare with cargo
(a workspace with path dependencies, dev profile, 4 parallel jobs). The scenarios are cold / noop / changing the body of a function in the bottom intermediate crate m0
(low-body) / changing the signature of a pub function in m0 (low-sig, users fixed too) / changing the app. We check that the output is the same as cargo's.

At first, each user crate re-expanded and re-analyzed the whole source of its transitive dependencies every time, so as dependencies grew, cargo caught up in cold and low-sig
(with 100 crates, cold 3718 ms (cargo 3250), low-sig 1581 ms (cargo 1578). Of the analysis, macro expansion took 1.5 seconds). What we fixed:
- Macro expansion of dependency crates happens once: each crate expands only its own part, with just the macro definitions of its dependency crates attached
- What is passed to users is the interface (`crates/syntax/src/stub.rs`): bodies of non-generic functions become `{ loop {} }` (the dependency
  crate compiles them itself). Generic functions, generic impls, traits, `const fn`, `-> impl Trait` and `async fn` are kept.
  The expansion and the interface are saved in `<name>.prep`. `ZUSTC_NO_DEP_STUB=1` gives the old behavior
- Cache entries (item summaries, function machine code) created by child processes building in parallel are returned to the parent, and crates in later groups inherit them through fork
  (monomorphization of the prelude and item summaries of dependency crates' items are the same across many crates: functions compiled in a 100-crate cold build went 11360 → 5984)
- Fine-grained fingerprint (`<name>.fp2`): only the hashes of the dependency crates' interface items reachable by name from the crate's own identifiers
  (impls are reached through the header's type and trait names, methods by name: errs on the side of including too much rather than missing something). Even if the old fingerprint
  differs, nothing is rebuilt if the fine-grained fingerprint is the same. Since bodies are removed, signatures of functions in dependencies of dependencies do not reach users
- With bodies removed, methods are no longer reached by name when the crate's own type is made into a `Box<dyn Tr>`: they are also compiled from vtable entries

- What is passed to users is only the items of the dependency crates' interfaces that are reachable by name from the crate (the same traversal as the fine-grained fingerprint).
  Everything else is blanked out (`use` is kept because it is needed for name resolution). This way, flattening, item summary, Program and prelude selection cover only what is used
  (for m50 with 100 crates, dependency items went from around 800 → 150). `ZUSTC_NO_DEP_PRUNE=1` turns it off.
  An impl's names are the trait and type names in its header; the inside of `impl<..>`, everything from `where` on, and primitive types are not counted, and trait implementations
  for std types (`Vec`, etc.) are reached by the trait name alone (`impl FromHex for [u8; 4]` was reachable from every crate that wrote `u8`)

After that, we made the machine code of prelude functions reused across crates (functions compiled in a 100-crate cold build went 5984 → 4973):
- The key of a closed prelude function (its body is in the prelude, it is non-generic or its type arguments are only prelude or primitive types, and it is not a closure) is
  only the compiler ID, the body, its own signature and `#[panic_handler]`. Signatures of referenced items were collected generously by the last segment of the name, so
  the user's `Acc5::push` got into the key of prelude functions that call `.push(`, making the key differ per crate
- Panic locations of prelude functions are lines inside the prelude (from `PRELUDE_LINE` = 49152 onward, the location table maps lines to the file `<zustc prelude>`).
  Selected prelude items are placed at their original lines (with newlines in between). Before, the base line for prelude locations changed with the length of the user's source and
  with the prelude selection, so the cache missed, and the output showed meaningless locations such as `src/main.rs:259`
- Instances of dependency crates' generic functions are also reused: for a function whose body is in the prelude or in dependency crate j and whose type arguments do not
  include this crate's types (a closed function), the key includes only the referenced items within "crates visible from j and from the crates of the type arguments' types". Panic locations
  are kept as lines within j's text: the trap table adds the position on the user side when the .o is written, and for locations passed as constants (index checks, assert_eq!,
  unwrap callers) j's tag (`crate_tag`) goes into the upper bits of the line, and at run time j's table is selected from the list of dependency crates' tables in the executable's table (`_xT__exe`)
  and looked up. As a side effect, this also fixed the lookup of constant-passed locations inside dependency crates through the executable's table
  (which had printed a different file and line). Added an out-of-range index inside a dependency crate's generic function to tests/workspace.
  In this benchmark there were only about 80 duplicates, so the cold time is within measurement noise (1088 to 1223 ms with 100 crates)
- We decided not to split Program into "dependency base + own items": measured, the Program stage is about 1 ms per crate
  (4% of the cold total, 2% of an app change), and the base (the reachable part of dependencies and the selected prelude) also differs per crate and cannot be shared

When a dependency crate changes (even just a body), cargo recompiles all its users. zustc, with its per-function cache and
interface fingerprints, rebuilds only the crates that use what changed. Remaining: each crate rebuilds the item summaries and
Program for the prelude (a little over 500 items) (the selected prelude differs per crate, so the whole Program is not shared). Most of the remaining cold time is function
compilation (Cranelift).
