# zurgo M0: Cargo packages built with zustc

Date: 2026-11-21

zustc had no way to build a Cargo package: its workspace build takes a hand-written list of crates. This is the first
milestone of mizchi/zust#28. It adds `crates/zurgo`, a Cargo-compatible driver (named zargo at first, but that crate
name is taken on crates.io). zurgo reads Cargo.toml and Cargo.lock, finds the sources, turns on features as cargo does,
and builds the graph with zustc's workspace build in the same process. `zurgo metadata` writes the JSON of
`cargo metadata`. The issue for proc macros, mizchi/zust#29, was written at the same time. Usage: [zurgo.md](../zurgo.md).

## 1. What it is made of

3,100 lines, with no crates.io dependency (serde_json only in the tests):

| module | lines | contents |
|---|---:|---|
| `toml.rs` | 529 | TOML: tables, arrays of tables, dotted and quoted keys, inline tables, the four kinds of strings, numbers, dates |
| `resolve.rs` | 592 | the package graph from Cargo.lock and the manifests, and feature activation |
| `manifest.rs` | 381 | Cargo.toml: targets with Cargo's auto-discovery, dependencies of the three kinds and under `[target]`, features, workspace inheritance |
| `metadata.rs` | 258 | the JSON of `cargo metadata` |
| `semver.rs` | 244 | versions and requirements, with Cargo's rules for `^`, `~`, wildcards and pre-releases |
| `platform.rs` | 223 | `cfg(..)` platform keys, with the values `rustc --print cfg` gives for x86-64 Linux and wasm32 |
| `compile.rs` | 217 | the zustc workspace (`CrateSpec`) and the build |
| `lock.rs`, `json.rs` | 354 | Cargo.lock, and cargo's registry index cache |

zust-core changes by one field: `CrateSpec::exe`, the name of a binary's executable. A package's library and binary
share the package's name, and zustc names a crate's files by its name, so zurgo gives the binary another crate name and
keeps the executable's name here.

## 2. Matching cargo metadata

The test compares `zurgo metadata` with `cargo metadata` on the test packages and on cratebench/ui's dioxus (344
packages) and leptos (180) apps, without a platform filter and with `--filter-platform` for wasm32 and for x86-64 Linux.
It compares packages, ids, targets, enabled features, edges and their `dep_kinds`. They are the same everywhere.

The first version followed the documented rules of cargo's feature resolver, and it differed in four ways. Each one
showed something about what `cargo metadata` reports:

- **`cargo metadata` gives the dependency resolver's graph, not the feature resolver's.** Features in it are unified
  over every kind and every platform. A weak `dep?/feat` pulls `dep` into the graph: toml's
  `std = ["serde_core?/std", ..]` gives toml an edge to serde_core, though toml's `serde` feature is off. `zurgo build`
  keeps the feature resolver's rules, which cargo builds with: a side for the host, no dev-dependencies, platforms
  checked, weak features that wait.
- **`--filter-platform` only filters edges.** An edge is shown if one of its declarations applies, and its `dep_kinds`
  then list every declaration, also those for other platforms. dioxus-logger's tracing-subscriber has
  `cfg(not(target_arch = "wasm32"))` in its kinds under the wasm32 filter, and tracing-subscriber's features include
  `fmt`, which only that declaration asks for.
- **`x/f` also turns on the feature named `x`** when `x` is an optional dependency and there is a feature of that name,
  explicit or implicit. yoke has `zerofrom = ["dep:zerofrom"]` and `derive = [.., "zerofrom/derive"]`, so `derive` turns
  the `zerofrom` feature on.
- **Packages that are not downloaded still count.** `cargo metadata --filter-platform` and
  `cargo fetch --target` leave out packages for other platforms: here 49 of the dioxus graph's 344 were not downloaded
  (windows-sys, rustix, ndk ...). Their dependencies can still turn features on in a shared package: bitflags's `std`
  comes only through them. cargo has their dependencies and features
  in its registry index cache (`registry/index/*/.cache`, a version and a JSON line per entry), and zurgo reads them
  from there. Cargo also prints a platform key from its parse (`cfg(target_os="hermit")` becomes
  `cfg(target_os = "hermit")`), and zurgo does the same.

On dioxus, `zurgo metadata` takes 39 ms and `cargo metadata --offline` 320 ms. `cratebench/ui/run.py` now reads its
graph from zurgo and uses cargo only to download (`cargo fetch`). Its output is the same as before.

## 3. Builds

- A path workspace builds and runs as its cargo build does:
  - a library and a binary of one name;
  - features through `default`, a dependency's `features = [..]` and `dep:`;
  - a dev-dependency that would not compile, which must not be built.

  The same build again does no work: every crate is fresh, and nothing is linked.
- The six cratebench crates from crates.io (fnv, adler2, hex, itoa, rustc-hash, cfg-if), each with its cratebench app,
  print what their cargo builds print.
- For the dioxus and leptos apps, `zurgo build` stops at the first proc-macro dependency it reaches, and names it
  (`const_format_proc_macros`, `futures-macro`) with mizchi/zust#29.

hex did not print what its cargo build printed: `<[u8; 4]>::from_hex(..)` returned an error. This was not zurgo: plain
`zustc build` of cratebench's hex printed the same. Bisecting found 61ae81a ("pick_overload finds the group of a
suffixed candidate"):

- Impls of one trait for `[u8; 4]` and `[u8; 2]` give functions of one name, `n` and `n#1`, in one overload group.
- The caller chooses one by the self type. Before 61ae81a, pick_overload did not find the group of the suffixed `n#1`,
  so that choice stood.
- Since then, it re-picked by the first argument. For `fn from_hex<T: AsRef<[u8]>>(hex: T)`, every candidate fits, so
  the first impl was called.
- Now a function without `self` is not re-picked among impls for other self types: its first argument says nothing of
  the self type. Overloads of one self type (`From<&str>` and `From<String>` for one type) are still picked by the
  argument.
- `tests/probe/assoc_fn_by_self_type.rs` covers both.

No CI job compares cratebench's outputs (the KPI job measures its times), so this went unnoticed for a day. zurgo's
test now compares them.

## 4. Not changed

`cratebench/run.py` still builds with `zustc build` and hand-written workspaces. The KPI job (`bench/kpi_track.py`)
measures cratebench's builds with it, and building through zurgo would change what that KPI measures. The same crates
are built through zurgo in zurgo's tests.
