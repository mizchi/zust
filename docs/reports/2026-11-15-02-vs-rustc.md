# Comparison with rustc (as of 2026-11-15, after adding overflow checks, panic messages, etc.)

Date: 2026-11-15

The environment has no wild installed, so the linker is chosen automatically (ld.lld).

Build time (`python3 bench/run.py 1000`, N = 1000 functions):

| tool | cold ms | no-op ms | 1-function edit ms | peak RSS (cold) | binary | cache / incr dir |
|---|---:|---:|---:|---:|---:|---:|
| zustc | 167 | 20 | **44** | **59 MiB** | 553 KiB | **642 KiB** |
| rustc `-Cincremental -Cdebuginfo=0` | 962 | 230 | 433 | 163 MiB | 5013 KiB | 22151 KiB |
| rustc `-O` (non-incremental) | 11604 | - | - | 147 MiB | 382 KiB | - |

A 1-function edit is about 10 times faster than rustc incremental. zustc is slower than in the earlier table (wild, before adding checks) because of the linker difference (wild 5ms / ld.lld 17ms), and because of the checks and the panic table.

Speed of the generated code (`python3 bench/runtime.py`, `bench/rt/*.rs`. Builds without cache; median of 3 runs for both build and execution. All outputs match rustc):

| Program | zustc | zustc `-O` | rustc (debug) | rustc `-O` | build ms (zustc / rustc debug / rustc -O) |
|---|---:|---:|---:|---:|---|
| fib (recursive fib(35)) | 86 ms (3.1x) | 68 ms (2.5x) | 97 ms (3.5x) | 27 ms | 44 / 106 / 127 |
| hashmap (1 million entry calls) | 212 ms (1.9x) | 144 ms (1.3x) | 723 ms (6.5x) | 112 ms | 55 / 162 / 289 |
| matmul (200×200, 5 times) | 225 ms (5.2x) | 94 ms (2.2x) | 657 ms (15x) | 43 ms | 67 / 168 / 268 |
| nbody (5 bodies, 1 million steps) | 747 ms (19x) | 203 ms (5.1x) | 1388 ms (35x) | 40 ms | 53 / 119 / 191 |
| → nbody (after the improvements below) | 437 ms (8.2x) | **91 ms (1.7x)** | 1423 ms | 53 ms | 64 / 129 / 183 |
| sieve (sieve up to 20 million) | 373 ms (4.0x) | 195 ms (2.1x) | 467 ms (5.0x) | 94 ms | 40 / 117 / 155 |
| sort (sorting 2 million elements, etc.) | 1178 ms (6.0x) | 892 ms (4.6x) | 2161 ms (11x) | 195 ms | 58 / 142 / 314 |
| → sort (after the improvements below) | 782 ms (3.8x) | **611 ms (2.9x)** | 2102 ms | 209 ms | 58 / 153 / 311 |
| strings (format! / split / parse) | 257 ms (6.3x) | 176 ms (4.3x) | 127 ms (3.1x) | 41 ms | 61 / 125 / 203 |

(The figures in parentheses are ratios to rustc `-O`.)

- zustc debug builds are faster than rustc debug builds except for strings (both include the checks). rustc debug is slow because it instantiates std's generic code (iterators, HashMap, etc.) without optimization.
- zustc `-O` is 1.3–5 times rustc `-O`. The gap is large for nbody, which loops over floating-point arrays by index (LLVM removes the loop and range checks and vectorizes), for sort with merge sort, and for strings with formatting.
- zustc builds are 2–3 times faster than rustc debug and 3–5 times faster than rustc `-O` (without cache; with incremental builds the gap is even wider, as in the table above).
- Improvements to nbody and sort (the same machine has about 20% noise, so the ratios are against rustc `-O` measured at the same time):
  - When an array of length C or more is indexed by the loop variable of `for k in 0..C` (C a constant), skip the range check (also in debug)
  - Within the same block, check the same index and length only once (also in debug)
  - `-O`: unroll loops with a constant count of up to 4 (k becomes a constant, and `d[k]` folds into a constant address)
  - `-O`: create the panic block for an index check per location, and build the location constants there (the hot path does not line up length, index, line and column in registers as block arguments)
  - Do not count iterations of non-enumerate for loops (one fewer variable carried through the loop)
  - sort / sort_unstable compare directly with `<` instead of calling a closure (one instruction for integers). The merge selects without branches
  - sort_by_key calls the key function directly (no comparison closure in between). binary_search also compares directly with `<=` / `==`
  - Remaining gap: calls to sort_by_key's key function (LLVM inlines them), and the sort algorithm (std uses pdqsort / driftsort)
