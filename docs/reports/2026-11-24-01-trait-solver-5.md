# The trait solver, part 5: the rest of the list

Date: 2026-11-24

After [part 4](2026-11-23-07-trait-solver-4.md), taking its "what is left" in order.

## Associated types

- A definition whose value is a generic struct (`impl<R: D> A<R> for AT { type AS = As<R>; }`) was registered
  after the structs' fields were resolved, so a field naming it (`struct S(<AT as A<DT>>::AS)`) found nothing.
  It is now registered right after the generic definitions are laid out, before the other structs
  (`wf/issue-48638.rs`, `mir/mir_struct_with_assoc_ty.rs`, `associated-types/recursive-enum-with-assoc-type-selfref.rs`,
  `traits/issue-103563.rs`).
- `Self::X` in a trait impl's method signatures is the impl's own X, with the impl's parameters as they are, also
  when X names a parameter only the trait's arguments bind (`impl<E> Structure<E> for Slice { type FfiPtr = (*const
  E::FfiUnit, usize); }`). `unsized/issue-40231-*.rs` get past their signatures now; they stop later, in type
  inference through `S::FfiPtr` in generic code.

## std's impls as clauses: measured, and done differently

Before building it, the failing compile-fail tests whose error is a std-trait bound that zustc accepts were
counted. Only `Copy` came up more than once (`String: Copy` ×4, `T: Copy` ×4, `[bool]: Copy`); the rest are the
program's traits with higher-ranked bounds, `Self` or generics. So instead:

- a type parameter lacks std's trait (Copy, Clone, Debug, ..) when its bounds are all traits zustc knows the
  supertraits of and none gives it (`TraitDb::placeholder_lacks`). It holds whatever the parameter is, so it is
  reported from the generic fn nothing calls (`where-clauses/where-clause-constraints-are-local-for-{trait,inherent}-impl.rs`);
- a trait's method naming `<Self as Tr>::X` needs `Self: Tr` from the trait, its supertraits or the method's where
  clause (`associated-types/associated-types-for-unimpl-trait.rs`, `associated-types-no-suitable-supertrait{,-2}.rs`,
  `associated-types-projection-to-unrelated-trait-in-method-without-default.rs`).

## Names in messages

The solver's messages name types as rustc does: an `impl Trait` argument's parameter is `impl Sync`, not
`__impl0`, and a name in a module is `Hidden`, not zustc's flattened `a__b__Hidden` (`traits::display_ty`,
`display_name`, with a unit test).

## "mismatched types" on valid code: a survey, and one fix

130 run-pass / check-pass / build-pass tests fail with "mismatched types". By the types involved:

| group | about | what it needs |
|---|---:|---|
| integer literals settled to `i32` before a later use asks for another type (`u8`, `usize`, `Box<isize>`) | 15 | type inference that keeps literal variables open across statements |
| unsizing into a struct (`&Foo<[u8; 3]>` to `&Foo<[u8]>`), `&[u8; 5] as *const [u8]` | 11 | fat pointers to unsized struct tails (layout and codegen) |
| a generic parameter left unsolved (`expected T0`) | 10 | inference of instance arguments in more positions |
| distinct closure types, fn items against closures | 5 | closure type unification |
| others | ~90 | one or two each |

Fixed here: `b.clone()` of a Box (or array) whose numeric literal is not settled yet keeps the literal open for
what the clone must be (`closures/closure-upvar-last-use-analysis.rs`). The first version shared the receiver's
whole type variable, which let a coercion's target flow back into the receiver (`let c: Box<dyn A> = v.clone()`
made `v` a `Box<dyn A>`: `coercion/method-return-trait-object-14399.rs` regressed); it is now limited to an
unsettled literal.

These groups are type inference and codegen rather than trait solving; they are the next work, in that order.
