# Test time: where it goes, what was cut, and a nextest-like `zurgo test`

Date: 2026-11-23

## Where the time went

CI's test job (run 638, on 7a38644) took 9m50s:

| step | time |
|---|---|
| install wild and valgrind | 5m21s (valgrind's 27 MB from a mirror at 94 kB/s: 4m46s) |
| `cargo build --release --workspace` | 52s |
| `cargo test --release --workspace` | 2m05s (24s building the test targets, ~100s running them) |
| `tests/compare.sh` | 22s |
| formal/connect | 51s (its dependencies were built every time: rust-cache did not keep them) |

The tests' time was in a few tests that each build and run a few hundred programs, one after another
(local, 4 cores):

| test | time |
|---|---|
| `driver2_cranelift` | 44.3s |
| `security` | 27.4s (valgrind: ~20s of it) |
| `driver2_inline` | 17.8s |
| `driver2`, `wasm` | 8.7s each |
| `ast_codegen` | 7.1s |
| `zurgo` | 6.3s |

`cargo test` also runs the test binaries one after another, so a binary with one long test leaves the other cores
idle.

The build: on its own, zust-syntax's release build is 11.9s, of which LLVM is ~10s and the crate-local ThinLTO
(`lto = false` with 16 codegen units) 4.8s. The critical path is base/ir -> syntax -> sema -> typeck -> core -> zurgo.

## What changed

- `tests/common/par.rs` (`par_map`, a work queue over the cores) for the serial loops: `driver2_cranelift` 44 -> 12s,
  `driver2_inline` 18 -> 5s, `driver2` 9 -> 3s, `ast_codegen` 7 -> 2s, zurgo's two registry tests 5 -> 2s each.
  Outputs go to a directory per source directory (`floats.rs` and `modules.rs` are in two of them).
- `security.rs`: a case with `//@ args` runs under valgrind once per exit code (the first run that exits 0, the first
  that panics) instead of on every run: 27 -> 15s. `ZUST_SECURITY_VALGRIND=all` runs every one. The two
  `todo(valgrind)` leaks are still caught (a hidden one would fail the test as "passes now"). The cases with the most
  runs start first.
- `tests/compare.sh`: one process per example, on every core: 30 -> 9s.
- cargo-nextest in CI (`.config/nextest.toml`, `--profile ci`): 71 -> 50s for the whole suite on 4 cores, against
  `cargo test` after the changes above. In those 50s the 4 cores are busy (190s of CPU), so ordering cannot win more:
  nextest's `priority` for the long tests was tried and gave nothing (53s).
- CI's test job: valgrind's packages are cached and installed (`--no-install-recommends`) in the background while the
  workspace builds; rust-cache keeps formal/connect's dependencies; `CARGO_PROFILE_RELEASE_LTO=off`.

The ThinLTO trade, measured locally:

| | release (as is) | `lto = "off"` |
|---|---|---|
| clean build of the tests | 162s | 87s |
| the workspace's crates only (CI's case) | 68s | 47s |
| zustc on examples/*.rs | 1.97s | 2.29s (+16%) |
| running the tests | 94s | 101s |

So only CI's test job turns it off; the release profile (what bench.yml measures) is unchanged.

The sum of the test times is 148s -> 83s with `cargo test`, and the suite takes 50s with nextest.

## A nextest-like `zurgo test`

zurgo has no `test` yet, and zustc has no `--test`. nextest's model (list the tests of each binary, run every test
in its own process, schedule all of them over the cores) fits zustc better than libtest's:

- The harness is small. It only has to print the tests (`--list --format terse`, libtest's protocol, so nextest can
  read it too) and run the one test named (`--exact <name>`). A panic exits 101, a `Result` test that returns `Err`
  exits 1: no `catch_unwind`, no threads, no output capture in the program. Written by hand, such a harness for a
  `mod tests` with `#[test]`, `#[should_panic]` and a `Result` test builds with zustc as it is (with the
  `#[cfg(test)]` taken out: zustc has no `--cfg` yet) and behaves so.
- `should_panic(expected = ..)`, `#[ignore]`, timeouts, retries and capturing the output are the runner's (zurgo's)
  job, done once for all binaries.

What it needs:

1. zustc: `--cfg test` (and `--cfg` in general); `--test`, which keeps `#[cfg(test)]` items, collects the `#[test]`
   functions (paths, `#[ignore]`, `#[should_panic]`) and adds the harness's `main`. A panic message should name the
   source file, not `src/main.rs`.
2. zurgo: `test`, which builds the test targets (the lib's unit tests, `tests/*.rs` against the lib, bins' unit tests)
   with the dev-dependencies, lists each, and runs every (binary, test) pair over `-j` workers: libtest's filters
   (`<filter>`, `--exact`, `--ignored`, `--include-ignored`, `--skip`), `--no-fail-fast`, a slow / hang timeout, the
   output of failures, and a summary with times. Doc tests are out of scope at first.
3. One step past nextest: zurgo keeps each test's last time (`target/zust/test-times`) and starts the longest first.
   Here that matters on a machine with more cores than this suite has long tests: started last, one long test runs
   alone at the end.

What it would give: `zurgo test` for the crates in cratebench (their unit tests are the next check of zustc after
`run`), and the 98 tests of rustc's tests/ui with `compile-flags: --test` (86 have a `#[test]`). It is a feature of
its own, not a speed-up of this repository's tests, which zustc does not build.
