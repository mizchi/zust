# The trait solver, part 4: fewer false errors

Date: 2026-11-23

Parts 1–3 made zustc reject more invalid programs. This part looks the other way: valid programs (tests/ui
run-pass and check-pass) that the trait machinery rejected.

## 1. The solver's own false `No`s

`solve_no_sound` promises that the solver never says `No` to a goal that holds, *for the impls zustc read*. Two
check-pass / run-pass tests were rejected by it. Both turned out to be places where zustc's view of the program
was stricter than the program, which the weakening rule (part 1) forbids:

- `overloaded/overloaded-autoderef-vtable.rs`: `call_fn_vals` took the receiver struct's type arguments as the
  impl's, in the struct's order. `impl<T, H: Helper<T>> Deref for WithHelper<H, T>` got T and H swapped, and the
  solver rightly said no to the swapped goal. The impl's parameters are now matched from its self type.
- `higher-ranked/.../issue-90950.rs`: zustc represents `Cow<'_, str>` as `__CowStr` and `Cow<'_, [T]>` as the
  prelude's `Cow<T>`, so an impl for `Cow<'_, T>` with a parameter T covers two zustc types, and its head as resolved
  covers only one. Such a head is now weakened to any type (`two_reps`).

## 2. `implements` where it is wrong

`Insts::request` rejected a call whenever `Program::implements` said no. That string-based check misses many
impls: `(): PartialEq`, `Range<i32>: Clone`, `i32: Foo<A = usize>`, `&F: Fn()`, `String: AsRef<T>`. Simply
believing only the solver (first attempt) lost 46 correct rejections, because `implements` is right about many std
traits the solver cannot judge (`Fn` on non-callables, `Future`, `Into`, `UnwindSafe`, derive bounds). The rule
now:

- a trait of the program's: only the solver's `No`;
- std's: `implements`' `No`, except where it is known to miss impls. These are std's blanket impls it does not
  model (`Borrow`, `Any`, `DoubleEndedIterator`), a `Fn` trait of a reference to a closure or type parameter (`&F`
  is every Fn trait F is, `&mut F` FnMut / FnOnce), `()`'s derivable traits (the solver answers those from std's
  list), and a bound that the instance's types make true (`AsRef<T>` with T = str, `Into<&'a str>`). That last one
  only ever takes a `No` back: substituting types into the text and asking again gave `implements` new strings it
  misjudged, a second try that rejected valid programs, so it is never a reason to reject.

The cases the old check had right for the wrong reason now have their real reasons:

- `dyn Tr<A = T>` is no Tr when T breaks a bound Tr puts on A (`dyn X<Y = str>` with `type Y: Clone`);
- unsized types are never `Copy` / `Clone` / `Sized` / `Default`, and values that are never callable (scalars,
  arrays, the program's structs) are never `Fn`;
- E0107 for a turbofish that names an `impl Trait` argument's parameter (`foo::<str, String>`).

The coercion to `dyn Tr` follows the same rule (the program's traits by the solver).

Accepting more programs exposed one miscompile: `() == ()` (and the other comparisons of `()`) panicked at run time.
It is now a constant.

Two compile-fail tests no longer pass. Both had been passing by accident: rustc's errors there are about lifetimes,
which zustc's `Ty` erases (`borrowck/implementation-not-general-enough-ice-133252.rs`,
`impl-header-lifetime-elision/dyn-trait.rs`).

## 3. Associated types with the trait's arguments

`<S as Trait<usize>>::Assoc` lost `usize` in the syntax tree, so the impl that defines `Assoc` was chosen by the
self type alone: the first one, or none when the definition depends on the trait's arguments
(`impl<X> Trait<X> for S { type Assoc = X; }`). A qualified path whose trait has type arguments is now the
associated type `#targs:Trait#Assoc` of the tuple of the self type and the arguments (as generic associated types
already were). When they are concrete, the definition is looked up with the impl's trait arguments
(`AssocDef::trait_args`), matched exactly by the solver's `mtch`. Otherwise, or when nothing matches, it falls back
to the lookup by the self type alone, so nothing that resolved before changes.

## Results

tests/ui, against the start of this part:

| kind | before | after |
|---|---:|---:|
| run-pass | 1832 | 1842 |
| check-pass | 1512 | 1520 |
| build-pass | 102 | 102 |
| compile-fail | 4539 | 4542 (1 of them accidental) |

One newly "passing" compile-fail test was rejected at its line for another reason (an unsupported cast); it is
listed in `bench/rust_ui_accidental.txt`. `cargo test --release --workspace`: 375 passed; the 2 that fail are
zust-analyzer's LSP hover tests, which need rust-src (not installed here).

New tests: `tests/compile_errors/trait_solver_dyn_binding_bound.rs`, `tests/compile_errors/turbofish_impl_trait_arg.rs`,
and `examples/trait_solver.rs` cases for each pattern that was rejected (an impl whose parameters are not in its
self type's order, `&F: Fn`, `T: Borrow<T>`, `(): PartialEq + Default`, `<Pick as Choose<u16>>::Out`).

## What is left

- "cannot find associated type" remains for `Self::X` inside the impl that defines X when X's definition names the
  impl's parameters that only the trait's arguments bind (`unsized/issue-40231-*.rs`), and for definitions whose
  value is a generic struct, which are registered after struct fields are resolved (`wf/issue-48638.rs`,
  `macros/type-macros-hlist.rs`).
- `implements` is still the judge for most of std's traits; making the prelude's impls solver clauses would make
  both directions exact.
- The largest source of false errors on valid code is not traits: "mismatched types" (122 tests), mostly type
  inference and coercions.
